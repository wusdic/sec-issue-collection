# 通用数据采集平台 · 任务模式与参数库(v1.5)

> 运行单位从"需求画像"升级为"**任务**":每新建一个任务,就规定这个任务要干什么(采集什么信息)、多久干一次(节奏)、
> 用什么参数(范围/来源/记录形态/质量/输出…)。任务里**有共性的参数提炼进"参数库"**,以备其它任务直接复用;
> 任务只写自己特有的部分。引擎不变:任务**编译**成需求画像(引擎契约),再按画像跑。

## 1. 三层概念

```
参数库(preset)          任务(task)                         画像(profile)              运行
可复用片段  ──use──▶  参数库引用 + 本任务覆盖 + 节奏/状态  ──编译──▶  引擎契约(NeedContext) ──▶ 采集/处理/输出/自动运维
config/library/**       config/tasks/<id>.yaml                  库表 need_profile.config     按 task.status 决定跑不跑
```

| 层 | 是什么 | 谁维护 | 落在哪 |
|---|---|---|---|
| **参数库** | 一段可复用的画像片段:地域词、行业词、文种、记录形态(Schema+角色+去重+报表+界面)、质量规则、可信度分级、节奏、输出目标、通知渠道、Mock 规则… | 需求负责人 / 运营从任务里提炼;开发者补平台级条目 | `config/library/<kind>/<id>.yaml`(文件即版本,进 git) |
| **任务** | 一次"要干的事":目标、状态、节奏、预算、引用哪些参数库条目、本任务特有的覆盖 | 新建任务的人 | `config/tasks/<id>.yaml` |
| **画像** | 任务编译出的完整参数(引擎唯一契约);老的 `need_<id>.yaml` 也是画像 | 由编译器产生;也可手写(不用参数库) | 库表 `need_profile.config`(含 `task` 元信息与 `compiled_from`) |

为什么不直接把任务当画像:画像是"引擎能吃的完整形态",几十个键;任务是"人要说的话",通常只有十几行 + 几个引用。
两者之间放一个编译器,人写得少、引擎不用改、参数库能复用。

## 2. 任务的参数全集(哪些是任务自己的,哪些该进库)

| 类别 | 参数 | 典型归属 | 说明 |
|---|---|---|---|
| 目标 | `task.id/name/owner/purpose` | 任务 | 只属于这个任务 |
| 生命周期 | `task.status`(draft/active/paused/finished)、`schedule.start/end` | 任务 | 自动化只跑 active 且在有效期内的任务 |
| 节奏与预算 | `schedule.mode/cadence/time_window_days/time_filters`、`budget.*` | **库**(节奏套餐)或任务 | 编译映射:cadence→`need.timeliness_sla`,time_window_days→`scope.time_window_days`,time_filters→`keywords.time_filters`,budget→`keywords.query_budget_*` |
| 范围 | `scope.regions/industries/topics/entities/doc_types` | **库**(地域词、行业词、文种)+ 任务(主体名单、主题) | 同义词是最值得复用的资产 |
| 必须提及 | `scope.require_mention` | 任务 | 是否严格由任务定 |
| 记录形态 | `record_schemas`、`record.*`、`dictionaries`、报表口径、界面定义 | **库**(记录形态包) | 一类记录(政策文档 / 招标公告 / 企业动态)一个包 |
| 质量 | `quality.screen` 规则、`extract_rules`、`assertions`、`scope_guard`、`relations` | 库(通用规则如三态金额)+ 任务(粗筛目标) | `screen.goal` 几乎总是任务特有 |
| 可信度与验证 | `sources.credibility_levels`、`verification`、`reputation_registry` | **库** | "只认官方"这类策略可复用 |
| 来源 | `sources.seed_file`、`discovery_file`、`column_discovery` | 库(某类站点的源包)或任务 | 源包可按行业/地域沉淀 |
| 关键词 | `keywords.groups/compose` | 库(动作词组、配方)+ 任务 | 任务只写自定义配方 |
| 输出与通知 | `outputs.exports/notify/digest/leads_engine/quality_scorecard` | **库** | 本地资料库、飞书通知等标准输出 |
| 合规与基准 | `compliance`、`benchmark` | 任务 | 每个任务自己声明 |
| 演示与离线 | `demo.samples`、`mock.*` | 任务(样例)+ 库(记录形态包自带抽取规则) | — |

**提炼的判断标准**(什么该进库):① 至少两个任务会用(地域/行业/文种/节奏/输出);② 与任务无关、与领域有关且稳定(记录形态、可信度策略、三态规则);③ 维护成本高(同义词表、官方域名录)。任务独有的目标、状态、粗筛目标、合规声明不进库。

## 3. 参数库条目格式

```yaml
preset:
  id: scope.region.jiangsu          # 命名:<kind>.<子类>.<名>,全局唯一
  kind: scope                       # scope | record | keywords | sources | quality | schedule | outputs | ui | mock | misc
  name: 江苏省(含地市别名)
  description: "…"
  tags: [地域, 江苏]
  applies_to: [事件型, 文档型, 对象型, 观测型]   # 适用记录原型
  version: 1
  provenance: {from_task: tender_watch, section: scope.regions, extracted_at: "2026-09-03"}
body:                               # 与画像同构的片段
  scope:
    regions: [{value: 江苏省, terms: [江苏, 南京, 苏州, 无锡, 常州, 南通]}]
```

首批条目(从现有任务提炼):`scope.region.jiangsu`、`scope.industry.cybersecurity`、`scope.industry.healthcare`、
`scope.doctypes.procurement`、`record.tender_notice`、`quality.official_only`、`quality.tristate_money_cn`、
`schedule.hourly_30d`、`schedule.daily_365d`、`outputs.local_library`、`outputs.notify.all_configured`。

## 4. 任务文件格式与编译规则

```yaml
task: {id, name, owner, purpose, status, priority, schedule: {mode, cadence, time_window_days, time_filters, start, end}, budget: {...}}
use: [scope.region.jiangsu, scope.industry.cybersecurity, record.tender_notice, quality.official_only, schedule.hourly_30d, outputs.local_library]
overrides: {与画像同构的本任务特有键}
```

编译(`tasklib.compile_task`):
1. 按 `use` 顺序把各条目的 `body` 深合并:字典递归;**两边都是列表 → 追加去重**(词表、规则天然可叠加);标量后者覆盖;`null` 不覆盖;
2. 再合并 `overrides`;
3. `task.*` 映射到画像键(见 §2 节奏行);`need.id/name/owner/priority` 取自 task;
4. 编译产物带 `task`(元信息)与 `compiled_from.use`,通过画像六要素校验后装载(`profiles.setup_task`:注册 + 词表 + 关键词自动生成 + 种子源)。
引用不存在的条目直接报错(不静默跳过)。`python -m app.cli task-compile <id>` 可只看编译结果。

## 5. 提炼流程(任务 → 参数库)

1. 任务跑过、参数被验证有效(例如江苏地域词的召回好);
2. `library-extract <任务id> <点路径> <新条目id> <kind> <名称>`(或 `POST /library/extract`):把该段存成条目,自动记 provenance;
3. 其它任务在 `use` 里引用;原任务也可改为引用(去掉自己那段);
4. 条目改动就是新版本(git 记录);`library-list` 能看到每个条目被哪些任务引用,改之前知道影响面。

## 6. 运行:任务的生命周期与调度

| 状态 | 含义 | 自动化 |
|---|---|---|
| draft | 编好了还没启用 | 不跑 |
| active | 正式运行 | 每日采集、自动运维、日报、导出、回访再核查都跑 |
| paused | 暂停(源出问题、预算用完、换季) | 不跑,数据保留;`PUT /tasks/{id}/status` 恢复 |
| finished | 完成(campaign 到期 / once 回填完) | 不跑,库与资料库可查可导出 |

`schedule.mode`:continuous(持续);campaign(有起止,过期自动不跑);once(一次性回填,跑完标 finished)。
多任务:每日调度按"激活且可跑"的任务逐个执行(`profiles.active_need_ids(runnable_only=True)`),互不影响。

## 7. 入口

| 动作 | 页面/接口/CLI |
|---|---|
| 看任务清单与状态 | `GET /tasks`(含是否已装载、是否可跑) |
| 看编译结果 | `GET /tasks/{id}/compile`、`cli task-compile` |
| 装载/更新任务 | `POST /tasks/{id}/setup`(admin)、`cli task-setup`;`cli init --need <id>` 也会自动识别任务文件 |
| 暂停/恢复/结束 | `PUT /tasks/{id}/status` |
| 参数库浏览 | `GET /library?kind=&tag=`、`GET /library/{id}`、`cli library-list` |
| 提炼进库 | `POST /library/extract`、`cli library-extract` |

## 8. 与旧方式的关系

- `config/need_<id>.yaml` 仍然有效:它就是"没有引用参数库的任务";`setup_need` 先找画像文件,没有再找任务文件。
- 首个实例(安全事件库)与政策库保留为完整画像样板;招标监测已改为任务文件(`config/tasks/tender_watch.yaml`),
  编译结果与原画像等价(测试对照)。
- 参数库条目的 `body` 与画像同构,所以任何画像的任何一段都能一键提炼。
