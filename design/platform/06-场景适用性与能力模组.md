# 通用数据采集平台 · 场景适用性复查与能力模组(v1.2)

> 复查目标:同一平台,不改引擎,只改画像,能否覆盖"医疗行业最新政策 / 某类招标·中标信息 / 安全法规 /
> 某省市地域的某类文件 / 某行业或厅局的政策要求 / 某企业的定向信息(含关键词自动生成)"。
> 复查结论:原 v1.1 把"处理什么记录"参数化了,但"**要什么范围**"(地域/行业/主题/主体/文种)还散在
> 提示词、词表文件和找源配方里,而且**关键词矩阵要人手写**、**流水线阶段是固定顺序**。v1.2 补了三块:
> `scope` 范围限定、`keywords` 关键词能力模块、`pipeline.stages` 阶段组合 + 能力注册表。

## 1. 场景矩阵(七类需求 → 画像怎么写)

| 场景 | 记录原型 | 主体 / 键 | 维度(dim1) | 范围限定 scope | 抽取深度 | 关键词来源 | 去重键 | 输出 |
|---|---|---|---|---|---|---|---|---|
| 网络安全事件库(首个实例) | 事件型 | 单位 / 信用代码 | 行业 | —(全国) | Schema(50+ 字段、三态金额) | 手写矩阵 + 进化 | 主体+地区 & 手段交集 & 14 天 | 线索/报表/日报 |
| 安全法规(policy_watch) | 文档型 | 发布机关 / 文号 | 主题 | —(全国) | Schema(政策) | 手写矩阵 | 文号 | 日报/追踪 |
| **医疗行业最新政策**(med_policy) | 文档型 | 发布机关 / 文号 | 主题 | industries=医疗卫生(含医疗/医院/医保…),require_mention | Schema(复用政策 Schema) | **自动生成**:行业×主题、行业×文种、行业×动作 | 文号 | 日报 |
| **某类招标/中标**(tender_watch) | 对象型 | 采购人 / 项目编号 | 行业(地区做覆盖维度) | regions=江苏(含市名),industries=网络安全,doc_types=公告类型,require_mention=regions,30 天窗 | Schema(招标;金额为普通数值) | **自动生成**:画像自定义三元配方 地域×行业×文种 | 项目编号 | 金额按地区汇总、缺中标人清单、回访"待公布中标人" |
| **某省市地域的某类文件**(nanjing_docs) | 文档型 | 发文单位 / — | 主题 | regions=南京市,topics=数据要素…,doc_types,require_mention=regions | **轻量**(无 Schema 文件) | 自动生成:地域×主题、地域×文种 | 发文单位+标题 | 日报 |
| **某行业/厅局的政策要求** | 文档型 | 发布机关 / 文号 | 主题 | entities=厅局名(含简称),industries,require_mention=entities | Schema 或轻量 | 自动生成:主体×主题/文种 | 文号 | 日报 |
| **某企业定向信息**(company_watch) | 观测型 | 企业 / — | 动态类型 | entities=企业名单(含别名),topics=动态类型,require_mention=entities | **轻量**(+ 画像追加字段 sentiment) | 自动生成:主体×主题;监控名单(WatchTarget)自动并入 | 企业+标题 & 30 天 | 日报;线索关闭 |

"厅局政策要求"与 med_policy / nanjing_docs 只差 scope 取值,不再单独建画像;"安全法规"即 policy_watch。

## 2. 复查发现的缺口与本次补齐

| # | 缺口(v1.1) | 场景影响 | v1.2 做法 |
|---|---|---|---|
| G1 | 地域/行业/主题/主体/文种没有统一声明位,只有 `need.regions` 推地域 TLD | 省市文件、企业定向无法表达"必须提到谁" | `scope.{regions,industries,topics,entities,doc_types}`(值 或 {value, terms/aliases})+ `require_mention` + `time_window_days`;同一份声明喂给关键词、粗筛提示词(范围说明+别名)、范畴闸门、覆盖度维度、找源配方 |
| G2 | 关键词矩阵靠人手写文件;日常检索展开写死"事件×行业 / 后果×单位" | 每个新需求都要先编几十个词 | `keywords` 能力模块:scope 派生词组 + 静态词组 + 监控名单 → 缺省配方(锚点×对象)或画像 `compose` 配方;可选模型扩展同义词;`setup_need` 无关键词文件时自动生成;`POST /keywords/generate`、`cli keywords-generate`、页面按钮 |
| G3 | 找源配方/自检词依赖 `discovery.yaml` 文件 | 新需求没文件就找不了源 | `sources.discovery_file` 缺省 None → 由关键词模块生成 `source_search_queries` + `query_recipes` |
| G4 | 覆盖度取值必须来自词表文件 | 新需求没词表 | 词表缺失时用 `scope` 对应维度(`coverage.scope_kind`)的取值 |
| G5 | 抽取必须有 JSON Schema 文件 | 企业动态/地域文件这类"标题+摘要+主体+分类"够用的需求被迫写 Schema | `pipeline.extract_mode: light`:按角色生成轻量 Schema(可追加 `light_fields`),角色缺省自动对齐 |
| G6 | 金额汇总只认三态通道 | 招标金额是普通数值 | `reports_engine.amount_sum.kind: plain` |
| G7 | 处理流水线固定顺序,不能增删 | 有的需求不要抽取/去重/闸门 | `pipeline.stages` 声明阶段名;`pipeline.STAGES` 每个阶段是独立函数 |
| G8 | 底层能力只能被流水线调用 | 想单独试粗筛/抽取/关键词/找源要写代码 | `capabilities` 注册表:统一签名 `fn(db, ctx, **params)`;`GET /capabilities`、`POST /capabilities/{name}/run`、`cli cap-list / cap-run` |
| G9 | 监控名单(WatchTarget)只有模型和接口,不参与检索 | 企业定向靠人工改矩阵 | 名单按 kind 并入词组(org/product→主体、topic→主题、region→地域) |
| G10 | 系统信封字段(event_id/status)写死 | 文档型 Schema 有自己的业务 status | `record.envelope`(v1.1 已补);本次 4 个新画像验证 |

## 3. 能力模组目录(底座能力,独立可调)

| 分组 | 能力名 | 输入 | 输出 | 组合在哪 |
|---|---|---|---|---|
| 采集 | `fetch` | url, render | 状态/最终链接/正文头 | 采集、体检、找源 |
| 采集 | `columns.find` | 站点根地址 | 相关栏目列表(按画像提示词打分) | 栏目定位任务 |
| 处理 | `screen` | title, text | is_candidate/relevance/reason | 阶段 `screen` |
| 处理 | `extract` | title, text | payload/violations/schema_errors | 阶段 `extract` |
| 处理 | `guard` | payload, text | 降级后的 payload + 违规 | extract 内部 |
| 处理 | `scope_gate` | payload, title, text | out_of_scope + 原因 | 阶段 `scope_gate` |
| 处理 | `dedup.record` | payload | 命中记录号 + 主体键 | 阶段 `dedup_record` |
| 处理 | `process_document` | doc_id | 阶段结果 | 采集收尾、人工重跑 |
| 关键词 | `keywords.groups` / `keywords.generate` / `keywords.expand` | expand / content | 词组 / 矩阵版本 / 查询列表 | setup、日常检索、找源 |
| 找源 | `prospect.queries` / `prospect.run` / `coverage.summary` | — | 找源词 / 候选渠道 / 覆盖度 | 自动运维 |
| 更新 | `followup.schedule` | event_id | 回访任务 | 发布后 |
| 输出 | `leads.generate` / `reports.heatmap` / `reports.amount` / `digest.build` | event_id / scope / day | 线索 / 报表 / 日报 | 发布后、日报任务 |

每个能力只从 `NeedContext` 取参;新增能力只需在 `capabilities.py` 登记一次,流水线、自动运维、API、CLI 同时可用。
"独立程序"的用法:`python -m app.cli cap-run extract --need tender_watch --params '{"title":"…","text":"…"}'`。

## 4. 验证(tests/test_scenarios.py,11 用例;总计 377 通过)
- 四个新画像**不带任何词表/种子/配方/关键词文件**装载成功,关键词矩阵自动生成并生效(主体×主题、地域×行业×文种、行业×主题…);监控名单加入后词组随之扩展;找源配方无文件自动生成。
- 医疗政策:MED 前缀、发布机关/文号/主题/文种落列;不提医疗行业的文件被范围闸门拦下。
- 招标中标:采购人/项目编号/地区/公告类型/中标人/金额(万元→元)落库;非江苏公告拦下;普通数值金额按地区汇总;招标阶段自动生成"待公布中标人"回访;缺中标人清单报表。
- 企业定向:轻量 Schema(含追加字段)、别名归一到正式名、不点名的综述拦下、提示词带范围说明与别名。
- 省市文件:地域/主题落列,他市文件拦下,覆盖维度取自 scope.topics。
- 阶段可组合:去掉抽取/闸门/去重只留 `screen → draft` 也能建记录;能力注册表可独立调用并在 CLI 列出;`/needs/{id}/ui` 暴露范围说明与抽取模式。
- 字面量扫描仍为 0(新增模块无行业词)。

## 5. 仍留给 P1 的
- 采集适配器层已是插件(RSS/列表/搜索引擎/公众号/微博),但"某类站点专用解析"(如政府采购网列表字段)仍走通用列表模板;需要字段级列表解析时加适配器。
- `expand_with_llm` 已接口化,离线 Mock 返回空;真实模型下的词质量需要人工抽检一轮后再放开默认。
- 多需求并发调度、告警/订阅输出、对标批次流程(见 01 P1/P2)。
