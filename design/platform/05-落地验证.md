# 通用数据采集平台 · 落地与验证记录(v1.1)

> 对应 01 实施方案的 P0 交付。本文回答三件事:**改了什么**(哪些模块从"写死安全库"改成"读画像")、
> **怎么验证的**(自动化测试 + 双需求 HTTP 冒烟 + 字面量扫描)、**新需求怎么接**(一份画像 + 三个词表文件)。

## 3. 新增一个需求(操作清单)
1. 复制 `config/need_sec_events.yaml` 为 `config/need_<id>.yaml`,至少填 02 文档"最小画像"9 项:`need.id/name`、`record_schemas[0].file/archetype`、`record.id_prefix`、`record.field_roles`(title/subject/dim1/grade/occurred_date…)、`quality.screen.goal`、`dictionaries.file`、`coverage.dictionary_key`、`sources.seed_file`、`benchmark.baselines`。其余维度全部有中性缺省。
2. 准备 Schema(JSON Schema,required 字段就是完备度缺省权重来源)、词表(`coverage.dictionary_key` 那一节给覆盖维度取值)、找源配方文件(`sources.discovery_file`:`source_search_queries` + `query_recipes`)、种子源清单。
3. 装载:`python -m app.cli init --need <id>`(或页面调用 `POST /needs/<id>/setup`;`init --all` 一次装载全部画像)。
4. 设默认(可选):`.env` `DEFAULT_NEED_ID=<id>` 或设置页「平台 · 默认需求」;每日自动化 `DAILY_NEED_ID=a,b` 可跑多个。
5. 前端无需改动:头部切换需求,页签/列/详情/仪表盘/日报由 `/needs/<id>/ui` 驱动。
6. 离线联调:画像里给 `mock.screen_keywords` 与 `mock.extract_rules`(regex / when_contains+append|value / when_path_contains),`LLM_PROVIDER=mock` 下 `demo/seed` 即可走通全链路。

## 4. 已知边界(P1)
- 物理查询列仍是安全库时代的列名(`industry_l1/org_name/severity/...`),语义由 `ROLE_COLUMNS` 决定;新增第 3 个维度或第 3 组标签需要加列(01 §1.4 已说明取舍)。
- 每日自动化按需求串行;多需求并发调度、告警型/订阅型输出、对标批次流程按 01 的 P1/P2 排期。
- 前端"设置""数据源""采集"三页本就与领域无关,未改;"回访/复核台/线索"页文案沿用平台词(回访/线索),页签名可由画像改。
