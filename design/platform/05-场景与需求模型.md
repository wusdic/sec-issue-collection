## 1. 需求空间的六根轴

> 本章把"要采什么"拆成六个彼此独立的问题。任务文件就是按这六个问题填值:范围与节奏多来自参数库,对象与输出多来自记录形态条目,深度与生命周期按任务定。

| 轴 | 问题 | 取值 | 任务里的落点 |
|---|---|---|---|
| **W 对象**(what) | 记录的是什么 | 事件型 / 文档型 / 对象型 / 观测型 | 记录形态条目 `record.*`(`record_schemas[].archetype`、`field_roles`、`dedup`、`record_types`) |
| **S 范围**(which) | 要哪一片 | 地域 × 行业 × 主题 × 主体名单 × 文种 × 时间窗;每维可"必须提及" | `scope.*` 条目 + `overrides.scope.require_mention`;`task.schedule.time_window_days` |
| **F 来源**(where) | 从哪来 | 官方站栏目 / 平台号 / 搜索引擎 / RSS / 聚合站 / 名录;地域偏好 | `sources.seed_file`、`sources.discovery_file`(可省→按 scope 生成)、`region_policy`、`column_discovery` |
| **D 深度**(how deep) | 抽多细、多严 | 轻量(标题/摘要/主体/分类)/ Schema;断言三态开/关;确认等级 | `pipeline.extract_mode / light_fields`(记录形态条目)、`quality.*` 条目(`official_only`、`tristate_money_cn`) |
| **L 生命周期**(how it changes) | 入库后还变不变 | 一次性 / 状态跃迁(文号)/ 持续补全(回访)/ 持续跟踪(名单) | `update.*`、`record.dedup.window_days`;`task.schedule.mode` |
| **O 输出**(for what) | 给谁用 | 日报 / 交叉表 / 金额汇总(三态或数值)/ 状态计数 / 缺字段清单 / 线索 / 本地资料库 | `outputs.*` 条目(`local_library`、`notify.*`)、`reports_engine`、`digest`、`leads_engine.enabled` |

关键词生成不是一根轴,是 **S 轴的派生物**:词组 = scope 五维 + 静态词组 + 监控名单;配方 = 锚点(主体/地域/行业)× 对象(主题/事件/动作/文种)。
节奏(多久一次)不是轴而是任务元信息:`task.schedule`。

## 2. 决策表:需求特征 → 任务怎么写

> 本章把常见的需求说法直接翻译成"use 哪个条目、overrides 写什么"。没有现成条目时先写在 overrides,跑顺后提炼。

| 需求特征 | use(参数库) | overrides / task(本任务) |
|---|---|---|
| "只要 X 省/市的" | `scope.region.<x>`(如 `jiangsu` / `nanjing`;没有就新建) | `scope.require_mention: [regions]`;找源词自动带地域 |
| "只要 X 行业的" | `scope.industry.<x>`(`cybersecurity` / `healthcare`) | `scope.require_mention: [industries]`;`coverage.scope_kind: topics` 让覆盖度按主题看 |
| "只要某几家企业/某厅局的" | — | `scope.entities: [{value: 正式名, aliases: […]}]`,`require_mention: [entities]`;运行中可往监控名单加 |
| "某类文件(通知/办法/公告)" | `scope.doctypes.*`、`record.policy_document` 或 `record.light_document` | `record.dedup.subject_roles: [subject_key(文号), subject+title]` 已在条目里;`window_days` 放大 |
| "招标/中标这类有编号、有金额的对象" | `record.tender_notice`、`scope.doctypes.procurement` | `amount_sum.kind: plain`、`followup_triggers` 盯"未公布中标人"(已在条目里) |
| "事件,后续会有罚款/判决/整改" | `quality.tristate_money_cn`、`quality.official_only` | 事件型记录形态;`followup_triggers status_in [仅声称…]`;线索引擎按需开 |
| "先看个大概,不要 50 个字段" | `record.light_document` | 需要的字段用 `pipeline.light_fields` 追加;`field_roles` 只改要改的角色 |
| "不需要 LLM 抽取,只要收集标题" | — | `pipeline.stages: [screen, draft]` |
| "没有词表/关键词/种子/配方文件" | 任意 | 都省略:关键词按 scope 生成、找源配方按 scope 生成、覆盖度取自 scope、Schema 用轻量 |
| "要自动扩关键词" | — | `keywords.expand_with_llm: true`,或运行中 `query_evolution` 挖词 |
| "多久一次 / 只采最近的" | `schedule.hourly_30d` / `schedule.daily_365d` | 或直接写 `task.schedule.cadence / time_window_days / time_filters` |
| "只认官方 / 法规类" | `quality.official_only` 或 `quality.official_first_policy` | `confirm_allowed: [S1]` |
| "结果要落到本地能翻 / 要推飞书" | `outputs.local_library`、`outputs.notify.all_configured` | `outputs.exports[].path_template` 改目录心智顺序 |
| "同一类需求换个地域/行业再来一份" | 同一组条目,换掉地域/行业条目 | 只改 `task.id/name/purpose` 与 `screen.goal` |

## 3. 场景矩阵(七类需求 → 任务样板)

> 本章列出五个任务样板与首个实例,并说明"厅局政策要求"与"安全法规"如何由现有样板换范围得到。每一行都是同一套引擎、不同任务。

| 场景 | 任务 | 记录原型 | 主体 / 键 | 维度(dim1) | 范围限定 | 抽取深度 | 关键词来源 | 去重键 | 输出 | 引用的条目 |
|---|---|---|---|---|---|---|---|---|---|---|
| 网络安全事件库(首个实例) | `sec_events`(手写画像) | 事件型 | 单位 / 信用代码 | 行业 | —(全国) | Schema(50+ 字段、三态金额) | 手写矩阵 + 进化 | 主体+地区 & 手段交集 & 14 天 | 线索/报表/日报/资料库 | —(完整画像样板) |
| 安全法规 | `policy_watch` | 文档型 | 发布机关 / 文号 | 主题 | —(全国) | Schema(政策) | 手写矩阵 | 文号 | 日报/追踪/关系谱系/资料库 | `record.policy_document`、`quality.official_first_policy` |
| 医疗行业最新政策 | `med_policy` | 文档型 | 发布机关 / 文号 | 主题 | industries=医疗卫生(必须提及) | Schema(复用政策) | 自动生成:行业×主题、行业×文种、行业×动作 | 文号 | 日报 | `scope.industry.healthcare`、`scope.topic.healthcare_policy`、`record.policy_document` |
| 某类招标/中标 | `tender_watch` | 对象型 | 采购人 / 项目编号 | 行业(地区做覆盖维度) | regions=江苏(必须提及),industries=网络安全,doc_types=公告类型,30 天窗 | Schema(招标;金额为普通数值) | 自动生成:地域×行业×文种 | 项目编号 | 金额按地区汇总、缺中标人清单、回访"待公布中标人"、资料库 | `scope.region.jiangsu`、`scope.industry.cybersecurity`、`scope.doctypes.procurement`、`record.tender_notice`、`quality.official_only`、`schedule.hourly_30d`、`outputs.local_library` |
| 某省市地域的某类文件 | `nanjing_docs` | 文档型 | 发文单位 / — | 主题 | regions=南京市(必须提及),topics,doc_types | 轻量(无 Schema 文件) | 自动生成:地域×主题、地域×文种 | 发文单位+标题 | 日报 | `scope.region.nanjing`、`scope.topic.data_gov`、`record.light_document` |
| 某行业/厅局的政策要求 | (由 med_policy 或 nanjing_docs 换范围) | 文档型 | 发布机关 / 文号 | 主题 | entities=厅局名(含简称),industries,require_mention=entities | Schema 或轻量 | 自动生成:主体×主题/文种 | 文号 | 日报 | 同上 + `overrides.scope.entities` |
| 某企业定向信息 | `company_watch` | 观测型 | 企业 / — | 动态类型 | entities=企业名单(含别名,必须提及),topics=动态类型 | 轻量(+ 追加字段 sentiment) | 自动生成:主体×主题;监控名单自动并入 | 企业+标题 & 30 天 | 日报;线索关闭 | `scope.topic.company_dynamics`、`record.light_document` |

## 4. 缺口与补齐记录

> 本章记录泛化复查时发现的缺口与补法(v1.2),解释今天这些参数为什么存在。当时的复查目标:同一平台不改引擎,只改配置,能否覆盖上述七类需求。

| # | 缺口(v1.1) | 场景影响 | 补法 |
|---|---|---|---|
| G1 | 地域/行业/主题/主体/文种没有统一声明位 | 省市文件、企业定向无法表达"必须提到谁" | `scope.{regions,industries,topics,entities,doc_types}` + `require_mention` + `time_window_days`;同一份声明喂给关键词、粗筛提示词、范畴闸门、覆盖度、找源配方(v1.5 起可 `use` 参数库条目) |
| G2 | 关键词矩阵靠人手写文件 | 每个新需求都要先编几十个词 | `keywords` 能力模块:scope 派生词组 + 静态词组 + 监控名单 → 配方组合;可选模型扩展;装载时自动生成 |
| G3 | 找源配方/自检词依赖配方文件 | 新需求没文件就找不了源 | `sources.discovery_file` 缺省 None → 由关键词模块生成 |
| G4 | 覆盖度取值必须来自词表文件 | 新需求没词表 | 词表缺失时用 `scope` 对应维度(`coverage.scope_kind`) |
| G5 | 抽取必须有 JSON Schema 文件 | "标题+摘要+主体+分类"够用的需求被迫写 Schema | `pipeline.extract_mode: light`:按角色生成轻量 Schema(可追加 `light_fields`) |
| G6 | 金额汇总只认三态通道 | 招标金额是普通数值 | `reports_engine.amount_sum.kind: plain` |
| G7 | 处理流水线固定顺序 | 有的需求不要抽取/去重/闸门 | `pipeline.stages` 声明阶段名;`pipeline.STAGES` 每个阶段是独立函数 |
| G8 | 底层能力只能被流水线调用 | 想单独试粗筛/抽取/关键词/找源要写代码 | `capabilities` 注册表:统一签名;`GET /capabilities`、`POST /capabilities/{name}/run`、`cli cap-list / cap-run` |
| G9 | 监控名单不参与检索 | 企业定向靠人工改矩阵 | 名单按 kind 并入词组 |
| G10 | 系统信封字段写死 | 文档型 Schema 有自己的业务 status | `record.envelope` |
| G11(v1.5) | 共性参数在每个画像里重复 | 新需求要复制粘贴几十行 | 参数库 + 任务编译(01) |

## 5. 能力模组目录(底座能力,独立可调)

> 本章列出可单独调用的能力。每个能力只从 `NeedContext` 取参;新增能力只需登记一次,流水线、自动运维、API、CLI 同时可用。

| 分组 | 能力名 | 输入 | 输出 | 组合在哪 |
|---|---|---|---|---|
| 采集 | `fetch` | url, render | 状态/最终链接/正文头 | 采集、体检、找源 |
| 采集 | `columns.find` | 站点根地址 | 相关栏目列表(按任务提示词打分) | 栏目定位任务 |
| 处理 | `screen` | title, text | is_candidate/relevance/reason | 阶段 `screen` |
| 处理 | `verify` / `verify.recheck` | title, text / event_id | 验证状态 / 内容是否变化 | 阶段 `verify`、自动运维 `recheck` |
| 处理 | `extract` | title, text | payload/violations/schema_errors | 阶段 `extract` |
| 处理 | `guard` | payload, text | 降级后的 payload + 违规 | extract 内部 |
| 处理 | `scope_gate` | payload, title, text | out_of_scope + 原因 | 阶段 `scope_gate` |
| 处理 | `dedup.record` | payload | 命中记录号 + 主体键 | 阶段 `dedup_record` |
| 处理 | `relations.extract` | event_id, text | 关系边 | 阶段 `relations` |
| 处理 | `process_document` | doc_id | 阶段结果 | 采集收尾、人工重跑 |
| 关键词 | `keywords.groups` / `keywords.generate` / `keywords.expand` | expand / content | 词组 / 矩阵版本 / 查询列表 | setup、日常检索、找源 |
| 找源 | `prospect.queries` / `prospect.run` / `coverage.summary` | — | 找源词 / 候选渠道 / 覆盖度 | 自动运维 |
| 更新 | `followup.schedule` / `followup.recheck` | event_id | 回访任务 / 变化提示 | 发布后、自动运维 |
| 输出 | `leads.generate` / `reports.heatmap` / `reports.amount` / `digest.build` / `exports.run` / `notify.send` / `benchmark.run` | event_id / scope / day / … | 线索 / 报表 / 日报 / 导出 / 通知 / 召回 | 发布后、日报任务、自动运维 |

"独立程序"的用法:`python -m app.cli cap-run extract --need tender_watch --params '{"title":"…","text":"…"}'`。

## 6. 已知的轴外需求(不承诺、说清楚)

- 非中文/境外源为主的需求:适配器与地域策略可配,但 Mock/提示词默认中文语境;需要一轮真实模型验证。
- 需要登录/付费接口的来源:平台只做公开渠道(合规边界),不在范围内。
- 站点专用字段级解析(如政府采购网列表字段):走通用列表模板,需要精细字段时加适配器。
