# 通用数据采集平台 · 总纲(v1.3)

> 读设计文档从这里开始。本文回答"这个平台到底要把什么做好",其余文档(01–09)是它的展开。

## 1. 使命:围绕"想要的信息"做五件事

平台的主线只有一条:**针对一个信息需求,快速找到、尽可能找全、确认真实、整理成好用可用的记录、按分类存在本地。**
通知、导出、日报这些是把结果"送出去"的**功能组件**,按需调用,不是主线。

| 目标 | 一句话定义 | 平台靠什么做到 | 怎么量化(评分卡/看板) |
|---|---|---|---|
| **找得快** | 信息一公开,尽快进库 | 分级抓取间隔(时效 SLA 反推)、官方 JSON 接口直采、搜索引擎定题检索、公众号/平台号通道、翻页早停、时效窗口 | 披露→入库中位时延;引擎/源体检可用率 |
| **找得全** | 该有的都有,不漏 | 范围限定 scope → 关键词自动生成与进化、六通道源发现与主动找源、覆盖度盘点(缺哪块找哪块)、根域源栏目定位、对标基准漏报率 | 覆盖度(维度有覆盖比例)、候选渠道增长、漏报率 |
| **真实可信** | 每条都能说清"从哪来、可不可信" | 来源可信度分级 + 发布主体信誉名录、真实性验证(官方域/正文哈希/标题一致/密级标记)、断言三态(声称/估算/确认)与发布红线、可追溯校验、再核查内容变化 | 可追溯率、验证状态分布、守卫违规率 |
| **好用可用** | 结构化、干净、无重复、能直接用 | Schema 抽取(或轻量抽取)+ 画像规则、三层去重(URL/同稿/记录)、范畴闸门、完备度评分、复核双签、回访补全滞后字段、记录关系谱系(废止/替代/修订/依据) | 完备度均分、重复率、Schema 校验通过率、关键列填充率 |
| **分类存本地** | 按需求/维度/等级/时间落成可直接翻的本地资料库 | 当刻存档(原文/图片/附件/截图,哈希校验)、角色化查询列、本地资料库导出(`local_library`:JSON + Markdown + 快照路径,按路径模板分目录)、数据库主存储 | 存档覆盖率、存档抽检通过率、分类分布 |

五个目标对应质量评分卡的四维:找得全→完整性,真实可信→准确性,好用可用→一致性,找得快→时效性;
"分类存本地"是所有结果的落点,由存档覆盖率单独看。

## 1.5 运行单位:任务(v1.5)

平台以**任务**为运行单位:新建一个任务 = 规定要采集什么、多久一次、用哪些参数;任务里有共性的参数提炼进
**参数库**(地域词、行业词、记录形态、可信度策略、节奏、输出…)供其它任务 `use`;任务编译成需求画像后引擎照常跑。
详见 10 任务模式与参数库。

## 2. 信息获取闭环(主线)

```
        ┌──────── 范围限定 scope(地域/行业/主题/主体/文种/时间窗)────────┐
        │                                                                   │
  关键词生成/进化 ──→ 定题检索 ──┐                                          │
  源发现/主动找源 ──→ 源库 ──────┼──→ 采集(抓取/渲染/存档/去重) ──→ 验证(真实性)│
  覆盖度盘点(缺哪块找哪块)──┘            │                                   │
                                          ▼                                  │
                       粗筛 → 抽取 → 范畴闸门 → 记录去重 → 草稿 → 复核/发布  │
                                          │                                  │
                          回访补全 ← 记录 ─┴─→ 关系谱系 → 本地资料库(分类存储)│
                                          │                                  │
                          评分卡/覆盖度 ───┴───────────── 反馈:找源词、缺口 ──┘
```

每一步都是独立能力(`capabilities` 注册表),按画像 `pipeline.stages` 组合;每一步只从 `NeedContext` 取参。

## 3. 主线之外的功能组件(可插拔,不影响主线)

| 组件 | 作用 | 插件点 | 说明 |
|---|---|---|---|
| **通知组件** `notify` | 把日报/告警送到人 | `notify.CHANNELS`:email / feishu / webhook(钉钉、企微、自建同一入口),新渠道登记一个函数 | 画像 `outputs.notify.channels` 选渠道;未声明用设置里配齐的渠道;能力 `notify.send` |
| **导出组件** `exports` | 把记录送到别的系统或本地目录 | `exports.run` 的 kind:`local_library`(本地分类资料库)/ `feishu_bitable`;新目标加一个分支 | 画像 `outputs.exports[]` 声明目标与字段映射 |
| 日报 `digest` | 每日汇总 | 画像 `outputs.digest` | 用通知组件送出 |
| 线索引擎 `leads` | 记录 → 商机 | 画像 `outputs.leads_engine`(可整体关闭) | 首个实例专用,其它需求默认关 |
| 报表内核 `kpi` | 交叉表/金额/状态/缺字段/评分卡 | 画像 `outputs.reports_engine` | 口径全由画像声明 |

## 3.5 角色与使用路径(谁在什么时候用什么)

| 角色 | 日常要做的事 | 用哪些功能(03 编号) | 效果最大化的习惯 |
|---|---|---|---|
| 需求负责人 | 定义"要什么":范围、记录、真伪规则、输出 | B1 scope、D2 抽取模式/规则、C1 可信度等级、D8 回访触发、G1 装载 | 先用轻量模式 + 一键演示跑通,再加 Schema;每个范围值给同义词 |
| 运营 | 让源库健康、关键词有效 | A2 配源、B2 关键词、B5/B6 找源与自检、B4 候选池、G3/G4 自动运维与体检 | 每周看一次候选池与"找源完成"结论;把霸榜的老域交给 -site 排除 |
| 分析员 | 看记录、报表、覆盖度、评分卡 | D10 列表/详情、F4 报表、B8 覆盖度、E3 本地资料库 | 从仪表盘卡片下钻;覆盖空白就是下周的找源方向 |
| 复核员 | 复核发布、合并重复、处理待定 | C5 复核台、D7 待定队列、C4 三态字段 | 先看来源等级与三态状态,再看正文;红线拦下的补来源而不是硬发 |
| 管理员 | 设置、账号、渠道、导出目标 | G6 设置页、F1 通知渠道、F5/E3 导出、G8 审计 | 缺省值尽量不改;改 LLM 后点"测试连通" |
| 开发者 | 扩展能力、渠道、适配器 | G5 能力注册表、08 扩展点、G9 守护测试 | 新东西只登记不改引擎;升级前跑三道守护 |
| 自动化 | 每日采集、自动运维、日报、导出 | A1/A8、G3、F2、E3 | 时间预算而不是条数上限;失败不拦后续 |
