## 1. 三层概念

> 本章定义任务模式的三个层次:**参数库**是可复用的片段,**任务**是"这一次要干的事",**画像**是编译产物、引擎唯一契约。
> 人只写任务;引擎只读画像;参数库让任务写得少、经验能沉淀。

```
参数库(preset)              任务(task)                            画像(profile)                运行
可复用片段  ──use──▶  参数库引用 + 本任务覆盖 + 节奏/状态  ──编译──▶  引擎契约(NeedContext)  ──▶ 采集/处理/输出/自动运维
config/library/**         config/tasks/<id>.yaml                     库表 need_profile.config      按 task.status 决定跑不跑
```

| 层 | 是什么 | 谁维护 | 落在哪 |
|---|---|---|---|
| **参数库** | 一段可复用的画像片段:地域词、行业词、文种、记录形态(Schema + 角色 + 去重 + 报表 + 界面)、质量规则、可信度分级、节奏、输出目标、通知渠道、Mock 规则… | 需求负责人 / 运营从任务里提炼;开发者补平台级条目 | `config/library/<kind>/<id>.yaml`(文件即版本,进 git) |
| **任务** | 一次"要干的事":目标、状态、节奏、预算、引用哪些参数库条目、本任务特有的覆盖 | 新建任务的人 | `config/tasks/<id>.yaml` |
| **画像** | 任务编译出的完整参数集(引擎唯一契约);手写的 `need_<id>.yaml` 也是画像 | 编译器产生;也可手写 | 库表 `need_profile.config`(含 `task` 元信息与 `compiled_from`) |

**为什么中间要有编译器**:画像是"引擎能吃的完整形态",几十个键;任务是"人要说的话",通常十几行 + 几个引用。
两者之间放一个编译器,人写得少、引擎不用改、参数库能复用;编译产物可查看、可对照,出了问题能定位到是哪个条目或哪段覆盖带来的。

## 2. 任务文件

> 本章说明任务文件的结构。一个任务文件分三段:`task`(这个任务是什么、什么状态、什么节奏)、`use`(引用哪些参数库条目)、
> `overrides`(本任务特有的画像键)。三段合起来就完整回答了"采集什么、多久一次、用什么参数"。

### 2.1 结构

```yaml
task:                                  # 一、这个任务是什么
  id: tender_watch                     #   任务 id = 需求 id(记录、源、词表都按它隔离)
  name: 江苏网络安全招标中标监测
  owner: 销售运营
  purpose: 及时发现江苏省内网络安全类项目的招标与中标公告,跟踪中标人与金额,支撑销售打单
  status: active                       #   draft / active / paused / finished;自动化只跑 active
  priority: B                          #   A/B/C:抓取与查询配额
  schedule:                            #   多久一次、采多久的内容
    mode: continuous                   #   continuous 持续 / campaign 有起止 / once 一次性回填
    cadence: hourly                    #   hourly / daily / weekly / alert → 画像 need.timeliness_sla
    time_window_days: 30               #   只采近 N 天 → scope.time_window_days
    time_filters: [近7天]              #   检索时间过滤 → keywords.time_filters
    start: null                        #   campaign 的起止;自动化只在区间内跑
    end: null
  budget:                              #   配额
    query_budget_per_source_daily: 200 #   → keywords.query_budget_per_source_daily
    max_pages_per_query: 3             #   → keywords.max_pages_per_query
use:                                   # 二、用哪些现成参数(按序合并,后者覆盖前者;列表追加去重)
  - scope.region.jiangsu               #   地域词(含地市别名)
  - scope.industry.cybersecurity       #   行业词
  - scope.doctypes.procurement         #   文种(招标/中标/变更/废标公告)
  - record.tender_notice               #   记录形态:Schema + 角色 + 去重键 + 报表口径 + 界面
  - quality.official_only              #   可信度:只有官方来源能支撑"已确认"
  - schedule.hourly_30d                #   节奏套餐
  - outputs.local_library              #   发布即落本地分类资料库
overrides:                             # 三、只有这个任务才有的(与画像同构)
  need: {primary_behaviors: [G1], languages: [zh], regions: [中国大陆]}
  compliance: {data_categories: [政府采购公开信息], personal_info: false, collection_boundary: 仅公开渠道, retention: 3年, usage_limit: 内部销售参考}
  scope: {require_mention: [regions]}  #   必须提到江苏才算范围内
  quality:
    model: 事实核实型
    screen:
      goal: 判断是否为江苏省内网络安全/信息安全类采购项目的招标、中标、变更、废标公告原文
      include_rules: [政府采购网/公共资源交易中心发布的公告原文, 采购内容涉及安全设备/等保测评/安全运营/数据安全]
      exclude_rules: [招标代理/培训/资讯解读, 非江苏省项目, 与安全无关的采购]
  benchmark: {baselines: [{name: 江苏政府采购网月度公告, type: 官方汇总, cycle: 月}], target_recall: 0.95}
  demo: {samples: [...]}               #   一键演示样例
```

### 2.2 每段的含义

| 段 | 回答的问题 | 必填 | 说明 |
|---|---|---|---|
| `task.id / name` | 这是哪个任务 | ★ | id 也是需求 id;name 进界面标题、提示词、日报 |
| `task.owner / purpose` | 谁负责、为了什么 | 建议 | purpose 一句话说清"要拿到什么、给谁用",是写粗筛目标的依据 |
| `task.status` | 现在跑不跑 | ★ | 见 §6 |
| `task.priority` | 配额优先级 | — | A/B/C;进画像 `need.priority` |
| `task.schedule` | 多久一次、采多久 | ★ cadence | 见 §4.3 映射 |
| `task.budget` | 每天查多少 | — | 不填用参数库或平台缺省 |
| `use` | 复用哪些共性参数 | — | 可以为空(全部手写在 overrides);引用不存在的条目直接报错 |
| `overrides` | 本任务特有 | ★ `quality.screen.goal`、`compliance` | 键与画像模板 `config/need_profile.template.yaml` 同构;最小需要:粗筛目标、合规声明、范围(scope)、对标基准 |

### 2.3 五个任务样板

| 任务文件 | 干什么 | 节奏 | 引用的条目 | 特有部分 |
|---|---|---|---|---|
| `tender_watch` | 江苏网络安全招标/中标 | 小时级 · 近 30 天 | 地域 + 行业 + 文种 + 招标记录形态 + 只认官方 + 节奏 + 资料库 | 必须提及地域、粗筛目标、关键词配方、金额守卫 |
| `policy_watch` | 安全领域法规/标准/征求意见稿 | 日级 | 政策文档记录形态 + 政策类可信度 | 词表/找源/种子文件、回访检索包、关系谱系 |
| `med_policy` | 医疗行业政策 | 日级 · 近 30 天检索 | 医疗行业词 + 医疗主题/文种 + 政策文档记录形态 | 必须提及行业、粗筛目标 |
| `company_watch` | 名单内企业公开动态 | 日级 · 近 7 天检索 | 企业动态类型 + 轻量记录形态 | 企业名单与别名、必须提及主体、倾向字段 |
| `nanjing_docs` | 南京市数据/政务类文件 | 日级 | 南京地域 + 数据政务主题/文种 + 轻量记录形态 | 必须提及地域、粗筛目标 |

`config/need_sec_events.yaml`(安全事件库)保留为**完整画像样板**,用来查每个键的写法;新任务不必照它写全。

## 3. 参数库

> 本章说明参数库条目的格式、分类、命名,以及"什么参数该进库"的判断标准。参数库是任务之间共享经验的地方:
> 一个条目就是一段与画像同构的片段,加上说明它是什么、适用什么、从哪来的元信息。

### 3.1 条目格式

```yaml
preset:
  id: scope.region.jiangsu            # 命名:<kind>.<子类>.<名>,全局唯一
  kind: scope                         # 分类,见 3.2
  name: 江苏省(含地市别名)
  description: "地域限定:江苏省及 13 个地级市别名"
  tags: [地域, 江苏]
  applies_to: [事件型, 文档型, 对象型, 观测型]   # 适用的记录原型
  version: 1
  provenance: {from_task: tender_watch, section: scope.regions, extracted_at: "2026-09-03"}
body:                                 # 与画像同构的片段;任务 use 时按序深合并
  scope:
    regions: [{value: 江苏省, terms: [江苏, 南京, 苏州, 无锡, 常州, 南通, ...]}]
```

### 3.2 分类(kind)

| kind | 放什么 | 典型条目 | 谁最常用 |
|---|---|---|---|
| `scope` | 范围词:地域、行业、主题、主体、文种(含同义/别名) | `scope.region.jiangsu`、`scope.industry.healthcare`、`scope.doctypes.procurement`、`scope.topic.data_gov` | 所有任务 |
| `record` | 记录形态包:Schema 引用 + 字段角色 + 记录类型 + 去重键 + 报表口径 + 界面 + Mock 规则 | `record.tender_notice`、`record.policy_document`、`record.light_document` | 同类记录的任务 |
| `quality` | 质量与可信度策略:可信度分级、三态守卫、闸门规则 | `quality.official_only`、`quality.official_first_policy`、`quality.tristate_money_cn` | 事实核实型任务 |
| `schedule` | 节奏套餐:SLA + 时效窗 + 时间过滤 | `schedule.hourly_30d`、`schedule.daily_365d` | 所有任务 |
| `outputs` | 输出与通知:本地资料库、多维表格、通知渠道、日报 | `outputs.local_library`、`outputs.notify.all_configured` | 所有任务 |
| `keywords` | 动作词组、关键词配方 | (待提炼) | 检索型任务 |
| `sources` | 某类站点的源包:种子清单、找源配方、栏目提示词 | (待提炼) | 同行业/地域任务 |
| `ui` / `mock` / `misc` | 界面定义、离线规则、其它 | (通常包含在 record 包里) | — |

### 3.3 什么该进库(提炼判断标准)

| 进库 | 不进库(留在任务) |
|---|---|
| ① 至少两个任务会用:地域词、行业词、文种、节奏、输出 | 任务目标、状态、负责人 |
| ② 与任务无关、与领域有关且稳定:记录形态、可信度策略、三态规则 | 粗筛目标 `screen.goal`(几乎总是任务特有) |
| ③ 维护成本高、验证过有效:同义词表、官方域名录、检索包链接 | 合规声明、对标基准 |
| ④ 平台级标准做法:发布即落资料库、通知用已配渠道 | 主体名单(除非是稳定的机构名录) |

### 3.4 现有条目(v1.5,18 条)

| kind | 条目 | 被哪些任务引用 |
|---|---|---|
| scope | `scope.region.jiangsu`、`scope.region.nanjing`、`scope.industry.cybersecurity`、`scope.industry.healthcare`、`scope.doctypes.procurement`、`scope.topic.healthcare_policy`、`scope.topic.company_dynamics`、`scope.topic.data_gov` | tender_watch / nanjing_docs / med_policy / company_watch |
| record | `record.tender_notice`、`record.policy_document`、`record.light_document` | tender_watch / policy_watch + med_policy / company_watch + nanjing_docs |
| quality | `quality.official_only`、`quality.official_first_policy`、`quality.tristate_money_cn` | tender_watch / policy_watch |
| schedule | `schedule.hourly_30d`、`schedule.daily_365d` | tender_watch |
| outputs | `outputs.local_library`、`outputs.notify.all_configured` | tender_watch |

`python -m app.cli library-list` 随时列出当前条目与引用关系(`used_by`)。

## 4. 编译规则

> 本章是任务 → 画像的精确规则,开发者与排错时看。编译器 `tasklib.compile_task` 只做三件事:按序合并、映射任务元信息、附上来源记录。

### 4.1 合并顺序

1. 按 `use` 顺序,把各条目的 `body` 依次深合并到空画像上(后者覆盖前者);
2. 再合并 `overrides`;
3. 把 `task.*` 映射到画像键(§4.3);
4. 附 `task`(元信息原样)与 `compiled_from.use`;
5. 装载时经画像六要素校验(缺项拒绝激活),缺的键由 `need_ctx.DEFAULTS` 中性缺省补齐。

### 4.2 合并语义

| 情况 | 规则 | 为什么 |
|---|---|---|
| 两边都是字典 | 递归合并 | 画像是嵌套结构 |
| 两边都是列表 | **追加去重**(按 JSON 序列化比较) | 词表、规则、样例天然可叠加;两个地域条目合起来就是两省 |
| 标量 | 后者覆盖 | 任务比条目更具体 |
| 后者是 `null` | 不覆盖 | 想"关闭"某个报表用画像自己的显式 null 语义(在 `overrides` 里直接写 null 也是合并后的值,见 02) |
| 引用不存在的条目 | 直接报错 | 不静默跳过,避免以为生效了 |

**推论**:列表只能追加不能删除。想"替换"一段列表,就不要引用含那段列表的条目,而是在 overrides 里完整写出。

### 4.3 任务元信息 → 画像键

| 任务键 | 画像键 | 说明 |
|---|---|---|
| `task.id / name / owner / priority` | `need.id / name / owner / priority` | 任务即需求 |
| `task.schedule.cadence`(hourly/daily/weekly/alert) | `need.timeliness_sla`(小时级/日级/周级/告警级) | 反推分级抓取间隔 |
| `task.schedule.time_window_days` | `scope.time_window_days` | 采集时效窗 |
| `task.schedule.time_filters` | `keywords.time_filters`(替换) | 检索时间过滤 |
| `task.budget.query_budget_per_source_daily / max_pages_per_query` | `keywords.*` 同名 | 配额 |
| `task.status / schedule.start / end / mode` | 编译产物 `task.*`(不进引擎参数) | 自动化门控 `tasklib.is_runnable` |

### 4.4 校验与报错

| 检查 | 时机 | 结果 |
|---|---|---|
| `task.id` 必填 | 编译 | 报错 |
| `use` 里每个 id 存在 | 编译 | 报错并列出缺失 id |
| 画像六要素(need / compliance / record_schemas / quality.screen / sources.credibility_levels / benchmark) | 装载 | 缺项拒绝激活 |
| 编译结果与手写画像的等价性 | 测试 | 五个任务样板都有对照(见 §10) |

## 5. 新建一个任务(操作流程)

> 本章是给需求负责人的步骤清单。目标是:**十几行 + 几个引用**就能跑起来,跑顺后再逐步加细。

| 步 | 做什么 | 看什么 / 常见错误 |
|---|---|---|
| 1 说清目的 | 用一句话写 `purpose`:要拿到什么信息、给谁用 | 说不清目的就写不好粗筛目标 |
| 2 选记录形态 | 决定记录原型(事件/文档/对象/观测)与抽取深度;`use` 一个 `record.*` 条目(轻量先用 `record.light_document`) | 先轻量后 Schema |
| 3 定范围 | `use` 地域/行业/文种条目;主题、主体名单写在 `overrides.scope`;决定 `require_mention` | 每个范围值都给同义/别名;主题写"事项级"词 |
| 4 定节奏 | `task.schedule`:mode / cadence / time_window_days / time_filters;或 `use` 一个 `schedule.*` 套餐 | 小时级只给真正需要的任务 |
| 5 定可信与输出 | `use` `quality.*`、`outputs.*` 条目;法规类只认 S1 | 通知渠道未声明即用设置里配齐的 |
| 6 写特有部分 | `overrides`:`quality.screen.goal / include_rules / exclude_rules`、`compliance`、`benchmark`、`demo.samples` | 粗筛规则写"情形"不写关键词 |
| 7 编译与装载 | `cli task-compile <id>` 看编译结果 → `cli task-setup <id>`(注册 + 词表 + 关键词自动生成 + 种子源) | 引用不存在的条目会报错;关键词生成后看"展开示例" |
| 8 跑通与提炼 | 界面切换到该任务 → 一键演示 → 首次部署流程 → 跑两周看评分卡;把验证有效的段 `library-extract` 进库 | 只改信号指向的那一个参数(02 调参指南) |

## 6. 运行与生命周期

> 本章说任务在什么状态下会被自动化执行、多任务怎么调度、怎么暂停恢复。原则:**用状态管理任务,不删文件**。

### 6.1 状态机

| 状态 | 含义 | 自动化(每日采集/自动运维/日报/导出/再核查) |
|---|---|---|
| `draft` | 编好了还没启用 | 不跑 |
| `active` | 正式运行 | 跑 |
| `paused` | 暂停(源出问题、预算用完、换季) | 不跑,数据保留;恢复用 `PUT /tasks/{id}/status` |
| `finished` | 完成(campaign 到期 / once 回填完) | 不跑;库与资料库可查可导出 |

### 6.2 schedule.mode

| mode | 含义 | 门控 |
|---|---|---|
| `continuous` | 持续监测 | 只看 status |
| `campaign` | 有起止 | status active 且 `start <= now <= end` |
| `once` | 一次性回填 | 跑完标 finished |

### 6.3 多任务

每日调度按"激活且可跑"的任务逐个执行(`profiles.active_need_ids(runnable_only=True)`),互不影响;一个源可以服务多个任务(`Source.serves_needs`);
记录、词表、回访、线索、报表全部按任务 id 隔离。

## 7. 提炼与复用

> 本章说怎么把任务里验证有效的一段参数变成参数库条目,以及条目改动的影响面怎么看。

1. 任务跑过、参数被验证有效(例如江苏地域词的召回好);
2. `cli library-extract <任务id> <点路径> <新条目id> <kind> <名称>`(或 `POST /library/extract`):把该段存成条目,自动记 `provenance`;
3. 其它任务在 `use` 里引用;原任务也可改为引用(去掉自己那段);
4. 条目改动就是新版本(git 记录);`library-list` 能看到每个条目被哪些任务引用,改之前知道影响面;
5. 条目的 `body` 与画像同构,所以**任何画像的任何一段都能提炼**,包括手写的 `need_sec_events.yaml`。

## 8. 入口

| 动作 | 页面 / 接口 / CLI |
|---|---|
| 看任务清单与状态 | `GET /tasks`(含是否已装载、是否可跑);`GET /needs` 也列出未装载的任务文件 |

## 9. 与手写画像的关系

> 本章说明老方式的兼容:手写画像文件仍然有效,它就是"没有引用参数库的任务"。

- `config/need_<id>.yaml` 仍然有效;`setup_need` 先找画像文件,没有再找任务文件并编译;无数据库会话时 `need_ctx.get` 也会按任务文件编译。
- 安全事件库(`need_sec_events.yaml`)保留为完整画像样板;其余五个需求都已是任务文件,编译结果与原手写画像逐段等价。
- 手写画像的任何一段都能 `library-extract` 成条目;反过来任何任务也能 `task-compile` 看到完整画像。
