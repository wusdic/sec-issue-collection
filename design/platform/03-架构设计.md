# 通用数据采集平台 · 架构设计(v2.0,模块式分层架构)

> 本文回答"**平台是怎么搭的、每一层承担什么需求、为什么这样分、怎么在不动别人的前提下改一层**"。

## 1. 架构总览

> 本章给出八层结构与依赖方向。关键是配置层的三级(参数库 / 任务 / 画像)与契约层(把画像翻译成 `NeedContext`),
> 它们让"新任务只是一份 YAML"与"引擎改一处不牵动全局"同时成立。

```
┌─ 界面层 ────────────────────────────────────────────────────────────────────────────┐
│ 单页管理台(任务切换 / 仪表盘 / 记录 / 复核台 / 回访 / 线索 / 数据源 / 采集 / 动作 / 日报 / 设置)   │
│ 只认 /needs/{id}/ui 给出的角色与定义,不认任何行业字段                                           │
├─ 接口层 ────────────────────────────────────────────────────────────────────────────┤
│ REST(/api/v1,JWT + 角色)· CLI(python -m app.cli)· 能力调用(/capabilities/{name}/run)         │
│ 任务与参数库:/tasks* /library*;task-compile / task-setup / library-list / library-extract        │
├─ 编排层 L2 ─────────────────────────────────────────────────────────────────────────┤
│ pipeline(采集入库 + 阶段化处理)· prospect(主动找源)· scheduler / crawl_runner(采集任务)        │
│ autopilot(自动运维 11 任务)· bootstrap(首次流程 8 步)· daily(每日调度,按任务状态门控)         │
│ profiles(任务/画像装载)· capabilities(能力注册表)· locate(批量栏目定位)                       │
├─ 能力层 L1 ─────────────────────────────────────────────────────────────────────────┤
│ 采集:adapters(源适配器注册表)columns health wechat                                              │
│ 处理:extraction money_guard dedup events review verify relations                                │
│ 关键词/找源:keywords discovery grading query_evolution                                          │
│ 更新/输出:followup leads kpi digest coverage exports benchmark                                   │
├─ 底座与契约层 L0 ───────────────────────────────────────────────────────────────────┤
│ 契约:need_ctx(画像 → 参数对象,角色↔列)tasklib(任务 → 画像 编译器,参数库)prompts(提示词)      │
│ 底座:llm(模型客户端/离线 Mock)fetcher(抓取/渲染/编码)archive(当刻存档)url_tools simhash          │
│       reputation(主体信誉)settings_service(运行时设置)actions(动作台账)notify(通知组件)diagnostics │
├─ 数据与存储层 ──────────────────────────────────────────────────────────────────────┤
│ SQLAlchemy 模型(SQLite 开发 / PostgreSQL 生产)· 存档目录(ARCHIVE_ROOT)· 本地资料库目录          │
├─ 配置层(纯数据)──────────────────────────────────────────────────────────────────┤
│ 参数库 config/library/<kind>/<id>.yaml  →  任务 config/tasks/<id>.yaml  →  画像(编译产物;或手写 need_<id>.yaml) │
│ 配套:Schema(JSON)· 词表 · 关键词矩阵 · 找源配方 · 种子源 · 信誉名录 · 产品映射(全部可省)          │
│ 运行时设置(.env + 设置页,库表 app_setting)                                                        │
└─────────────────────────────────────────────────────────────────────────────────────┘
依赖方向:上层 → 下层;同层(L1)不成环;服务层不引接口层;引擎代码零行业字面量。三条规则都有测试守护。
```

**为什么是这个分法**:平台要同时满足两类相互拉扯的需求——"不同任务差异极大"(法规/招标/企业动态/事件)与"引擎改一处不能牵动全局"。
把**差异全部压进配置层**(共性进参数库、特有写在任务),由**契约层**编译并翻译成统一参数对象,**能力层**每个模块只做一件事且只从契约层取参,
**编排层**只负责按名字把能力串起来,界面层只认角色。改任务不碰代码,改能力不碰编排,加渠道不碰主线。

## 2. 各层的需求与设计要求

> 本章每层按同一格式说明:承担的需求 → 职责边界 → 输入/输出 → 质量要求 → 依赖与扩展规则 → 禁止事项 → 包含模块 → 验证方式。

### 2.1 配置层(参数库 / 任务 / 画像与配套文件)

- **承担的需求**:让"新任务"只是一份 YAML;让不会写代码的需求负责人能表达"采集什么、多久一次、要什么范围、记录长什么样、怎么算真、怎么输出";让共性参数沉淀复用。
- **职责边界**:只放数据,不放逻辑。三级结构——参数库条目(可复用片段)→ 任务(引用 + 覆盖 + 节奏/状态)→ 画像(编译产物,入库)。画像可省略任何非必填键(中性缺省);配套文件全部可省(关键词/找源配方按 scope 生成、Schema 可用轻量模式)。
- **输入/输出**:人写任务 → `tasklib.compile_task` 编译 → `profiles.setup_task` 装载进库(NeedProfile + 词表 + 关键词 + 种子源)。手写画像走 `profiles.setup_need`。
- **质量要求**:最小画像即可上线;六要素与覆盖基准校验(缺项拒绝激活);引用不存在的条目直接报错;编译结果可查看、与手写画像逐段等价(测试对照);模板与文档同步。
- **依赖与扩展**:新增维度 = `need_ctx.DEFAULTS` 加中性缺省 + 02 登记;新增参数库条目 = 新文件或 `library-extract`;模板 `config/tasks/task.template.yaml`、`config/need_profile.template.yaml` 是权威样板。
- **禁止**:在任务或画像里写代码或路径以外的行为;在引擎里出现任务里的具体取值。
- **包含**:`config/tasks/*.yaml`、`config/library/**/*.yaml`、`config/need_*.yaml`、`schema/*.json`、`schema/*_dictionaries.yaml`、`config/keyword_matrix*.yaml`、`config/discovery*.yaml`、`config/seed_sources*.yaml`、`config/*_accounts.yaml`、`config/product_mapping_sec.yaml`。
- **验证**:`test_task_mode`(编译/装载/提炼/门控/场景任务)、`test_platform_generalization`(双需求)、`test_scenarios`(四任务)、`test_demand_matrix`(生成式 13 组合)。

### 2.2 契约层(need_ctx / tasklib / prompts)

- **承担的需求**:全平台唯一的取参入口;把任务的"意图"编译并翻译成引擎能直接用的参数、角色、提示词;保证没有画像也有中性行为。
- **职责边界**:`tasklib` 只读任务与参数库文件,做合并/编译/提炼/状态门控;`need_ctx` 做解析/合并/缺省/缓存、角色 → payload 路径 → 物理列三级映射、轻量 Schema 生成、界面定义 `to_ui()`、显式 null 语义、地域策略推导、Schema 文件加载;`prompts` 只由画像与 scope 组装提示词,含 `NEED_ID`/`SCHEMA_FILE` 标记供离线 Mock 对齐。
- **输入/输出**:`need_ctx.get(db, need_id)` / `for_need(np)` / `from_config(cfg)` → `NeedContext`;无会话时优先本进程缓存 → 查库 → 读画像文件 → 编译任务文件 → 中性缺省。
- **质量要求**:纯函数式(除缓存),毫秒级;线程安全;同一需求同一配置只构造一次;任何键缺失都不抛。
- **依赖与扩展**:只依赖 `config`/`settings`;**不得**引用能力层(有测试)。新角色 = `ROLE_COLUMNS` + 列;新参数 = `DEFAULTS`;新任务键映射 = `tasklib.compile_task`。
- **禁止**:读库与配置文件以外的 I/O;出现行业字面量;反向依赖能力层。
- **验证**:`test_module_boundaries::test_contract_layer_only_depends_on_itself`、字面量扫描、`test_task_mode`。

### 2.3 底座层(llm / fetcher / archive / url_tools / simhash / reputation / settings_service / actions / notify / diagnostics / errors)

- **承担的需求**:与领域无关的"硬能力":调模型、抓网页(含渲染/反爬/编码)、存档、URL 归一/跳转还原/平台号识别、同稿哈希、主体信誉、运行时设置、动作台账、通知渠道、诊断留痕。
- **职责边界**:每个底座模块只解决一类技术问题;不知道"记录"是什么;不读画像(通知组件例外:只读 `outputs.notify.channels`)。
- **输入/输出**:字节/URL/文本进,结构化结果出(`FetchResult`、`ArchiveManifest`、向量、归一化键、`(ok, note)`)。
- **质量要求**:可靠优先——超时/重试/降级链(渲染→httpx;存档 L-A→L-D);编码正确(头 → meta → 猜);限速与退避;离线可用(Mock 模型、无 Playwright 自动降级)。
- **依赖与扩展**:只依赖同层;新模型供应商 = `llm._build` 分支;新通知渠道 = `notify.CHANNELS` 登记;新反爬策略进 `fetcher`。
- **禁止**:依赖能力层/编排层;写业务规则。
- **验证**:`test_fetcher*`、`test_archive*`、`test_llm_compat`、`test_notify_and_library`。

### 2.4 能力层 L1(独立可调的功能模块)

- **承担的需求**:主线五目标的每一步都是一个可单独调用、可单独升级的模块(找源、关键词、粗筛、抽取、守卫、去重、验证、关系、回访、线索、报表、日报、覆盖、导出、对标、体检、栏目、定级、词进化)。
- **职责边界**:一个模块一件事;公开函数签名稳定;`ctx` 参数可省(缺省=默认任务);同层只能用彼此的公开函数且不成环。
- **输入/输出**:见 07 §2 的契约表;统一都能通过 `capabilities.run(name, db, need_id, **params)` 调用。
- **质量要求**:确定性(同输入同输出,便于回放);容错(模型异常/网络异常不抛到编排层,返回可解释结果);可观测(每步 `diagnostics.record`)。
- **依赖与扩展**:依赖 L0 与同层公开函数;新增能力 = 新模块 + `capabilities.register`;新增阶段 = 阶段函数 + `pipeline.STAGES`。
- **禁止**:引用编排层;跨模块用私有函数(`_x`);出现行业字面量;自行读任务/画像文件。
- **验证**:`test_module_boundaries`(无环、不向上)、各模块单测、`test_scenarios` / `test_demand_matrix`(跨任务)。

### 2.5 编排层 L2(把能力串成流程)

- **承担的需求**:采集一篇文档的完整链路、主动找源一轮、每日/自动运维/首次部署流程、任务装载;把"人不该按的按钮"变成到点自动跑;只跑 active 且在有效期内的任务。
- **职责边界**:只做顺序、并发、预算、状态落库与错误隔离;业务判断都在能力层。流水线阶段顺序由画像 `pipeline.stages` 决定;每日调度按 `profiles.active_need_ids(runnable_only=True)` 循环。
- **输入/输出**:任务参数进,`AutoOpsRun` / `CrawlJob` / `CrawlRun` 等运行记录出;进度可查、可取消、切页不丢。
- **质量要求**:幂等(种子载入、候选入库、日报 upsert);时间预算而非条数上限;单步失败不拦后续;SQLite 写锁友好(网络 I/O 前先提交);并发取号不撞主键。
- **依赖与扩展**:可依赖任何下层;新自动运维任务 = `autopilot.TASKS` 加一项;新首次流程步骤 = `bootstrap.STEPS`。
- **禁止**:写业务规则;直接读任务/画像文件(经 profiles / tasklib);引用接口层。
- **验证**:`test_autopilot_grading`、`test_bootstrap`、`test_crawl_job`、`test_parallel_crawl`、`test_concurrency`、`test_task_mode`(门控)。

### 2.6 接口层(REST / CLI / 能力调用)

- **承担的需求**:给界面、外部程序、运维脚本一个稳定入口;所有 `need_id` 缺省为平台默认任务;鉴权与角色;任务与参数库的管理入口。
- **职责边界**:参数校验、鉴权、调用编排层/能力层、审计日志;不含业务逻辑(试抓等已下沉到服务层)。
- **输入/输出**:JSON;错误用 HTTP 状态 + 中文 detail。
- **质量要求**:每个接口一个明确角色要求(admin / analyst / editor / reviewer / readonly);长任务全部异步 + 状态接口;接口对行业无感(角色键)。
- **依赖与扩展**:新接口只包一层服务函数;能力型功能优先走 `/capabilities/{name}/run` 而不是新增接口。
- **禁止**:服务层反向引用;在接口里写行业字面量。
- **验证**:`test_platform_generalization::test_needs_api_and_ui`、`test_task_mode::test_task_api_and_cli`、各接口用例、双需求 HTTP 冒烟(06 §3.1)。

### 2.7 界面层(单页管理台)

- **承担的需求**:让运营/分析/复核人员不看代码就能用;换任务不换界面。
- **职责边界**:启动拉 `/needs` + `/needs/{id}/ui`,页签/列/筛选/详情分区/仪表盘卡片/日报文案全部按定义渲染;数据源页按"自动化优先"排布(动作按钮收起,只留需要人拍板的)。
- **质量要求**:切页不丢后台任务状态(状态在服务端);每个数字有说明;错误可读。
- **依赖与扩展**:只认角色与 UI 定义;新页签需要后端 `to_ui()` 与前端一处路由。
- **禁止**:写死行业字段名、任务 id、页签名。

### 2.8 数据与存储层

- **承担的需求**:多任务隔离、可追溯、可回放、可迁移(SQLite ↔ PostgreSQL)。
- **职责边界**:35 张表分七组——需求与用户(need_profile / app_user / app_setting / audit_log)、源(source / source_metric_daily / source_discovery_evidence / source_probe / source_blacklist / keyword_set / keyword_run / search_query_stat / term_stat / watch_target / search_watermark)、采集(crawl_job / crawl_run / crawl_log / run_trace / raw_document / doc_cluster / archive_manifest)、记录(event / event_source / event_change_log / record_relation / review_task / dictionary_release)、更新与输出(followup_task / lead / daily_digest / benchmark_batch / benchmark_item)、运维(action_log / auto_ops_run)。
- **质量要求**:所有业务表带 `need_id`(= 任务 id);查询列由角色映射(语义在画像);轻量列迁移(`_ADDED_COLUMNS`,只加不改);存档文件带 manifest 哈希可抽检;`need_profile.config` 保存编译后的画像含 `task` 元信息。
- **禁止**:在表名/列名之外新增行业语义;跨任务共享记录。

### 2.9 运行与部署层

- 单进程可跑全部(FastAPI + 进程内调度线程 + 后台任务线程);可选 Celery/Redis 与 PostgreSQL;Playwright 可选(没有自动降级);LLM 供应商可换(OpenAI 兼容接口、离线 Mock);全部参数 `.env` + 设置页(库表)双通道,设置页改即时生效。
- 安全与合规:只采公开渠道;泄露站只登记元数据与截图;密级标记文档只登记不入库正文;JWT + 角色;审计日志;不贬损任何主体(线索话术规则)。

## 3. 贯穿各层的注册表(扩展点)

> 本章列出四个注册表。加功能只登记、不改别人;详细的扩展操作见 07 §3。

| 注册表 | 位置 | 登记什么 | 谁来消费 |
|---|---|---|---|
| 源适配器 `adapters._REGISTRY` | L1 | `name` → 适配器类(json_api / generic_rss / generic_list / 搜索引擎 baidu、bing、ddg、so360 / sogou_wechat / weibo_search / 专用站) | 种子源、找源、体检、试抓 |
| 流水线阶段 `pipeline.STAGES` | L2 | 阶段名 → `fn(db, need, ctx, doc, st, result) -> bool`(screen / verify / extract / scope_gate / content_check / dedup_record / relations / draft) | 画像 `pipeline.stages` |
| 能力 `capabilities._REG` | L2 | 能力名 → `fn(db, ctx, **params)` + 说明/参数 | REST `/capabilities`、CLI `cap-run`、前端 |
| 通知渠道 `notify.CHANNELS` | L0 | 渠道名 → `fn(subject, body, cfg)`(email / feishu / webhook) | 日报、告警、能力 `notify.send` |

参数库与任务文件不是注册表而是数据:新条目、新任务放进目录即被发现(`tasklib.library()` / `tasklib.task_files()`)。

## 4. 典型调用序列

> 本章用三条路径把各层串起来:自动采集一篇文档、首次部署、新建任务。

**A. 采集一篇文档(每日自动)**
`daily._tick`(只取可跑任务)→ `crawl_runner.start_job` → `pipeline.crawl_source`(适配器发现 → `ingest_item`:跳转还原 → URL 去重 → 时效窗 → 抓取/编码 → 同稿簇 → 引文/转载登记 → 存档)→ `process_document` 按 `pipeline.stages`:screen → verify → extract(+guard)→ scope_gate → content_check → dedup_record → [relations] → draft → `ReviewTask` → 复核发布 → `followup.schedule` / `leads.generate` / `relations.link` / `exports.on_publish`(发布即落资料库)→ 日报 → 通知组件 → 每日导出任务。

**B. 首次部署**
`bootstrap.start`:precheck(模型/渲染/引擎)→ seeds → engines(自检并只留可用)→ dedup → locate(根域源定位栏目)→ health → crawl(第一轮)→ prospect(此时覆盖空白与语料都有了)。

**C. 新建任务**
复制 `config/tasks/task.template.yaml` → 填 task 元信息与节奏 → `use` 参数库条目(地域/行业/记录形态/可信度/节奏/输出)→ 只写本任务特有的 overrides → `task-compile` 看结果 → `task-setup`(`tasklib.compile_task` → `profiles.setup_from_config`:注册 + 词表 + 关键词自动生成 + 种子源)→ 界面切换 → 一键演示 → bootstrap。跑顺后把值得复用的段 `library-extract` 进参数库。

## 5. 设计原则

> 本章是架构背后的规则,升级与评审时逐条对照。

1. **任务即运行单位**:每个任务规定采集什么、多久一次、用什么参数;参数为任务服务;共性参数进参数库复用。
2. **引擎零行业字面量**:`app/services` 与 `app/api` 里不允许出现任何具体行业/地域/产品词;出现即视为缺陷(测试扫描)。
3. **画像即契约**:编译后的画像是引擎唯一的个性来源;每个键都有 键名/类型/缺省/消费方;缺省 = 中性行为,老画像不改也能跑。
4. **平台常量 vs 任务参数**分清:平台常量(搜索引擎跳转域、通用大平台域、备案页脚域、跟踪参数、公共后缀、平台号识别、翻页/早停/反爬/渲染策略)与领域无关;其余全是任务参数(02)。
5. **范围先于字段**:任务先说清"要哪一片"(scope),再说"记录长什么样";范围一处声明,关键词、粗筛、闸门、覆盖度、找源都从它取。
6. **角色化而非改名**:物理查询列不改,语义由 `field_roles` 决定;接口同时返回物理名与角色名,前端只认角色。
7. **一处解析,处处复用**:所有模块只从 `NeedContext` 取参,禁止各自读 YAML。
8. **能力即模块,组合靠声明**:能力统一签名进注册表;阶段、运维任务、接口、CLI 都按名字调用;分层与依赖方向有测试守护。

### A.2 当时的目标架构

需求画像层(每需求一份纯数据)→ `profiles.load → NeedContext` → 通用引擎(源层 / 采集层 / 处理层 / 更新层 / 输出层 / 界面层)+ 平台常量层。
多需求并行:`NeedProfile` 表、`Source.serves_needs`、所有带 `need_id` 的表已隔离;缺的是调度/启动/首次流程按"全部激活需求"循环,以及默认需求收敛到 `settings.default_need_id`。
(v1.5 起,画像层前面再加了参数库与任务两级,见正文 §1。)

### A.3 分期(当时)

- **P0 契约与骨架**:`NeedContext` 52 项参数解析 + 缺省 + 缓存;`need_sec_events.yaml` 显式写全;政策库作为跨原型验证实例;14 个模块改读 `NeedContext`(H1–H20);默认需求收敛(H21);前端由 `ui` 段驱动(H22);演示数据进画像(H23);声明未消费项接线或标注(H24);Mock 改为 Schema 驱动。
- **P1 平台化补强**:画像 JSON Schema 校验;热加载与版本化;通用查询列迁移;告警/订阅输出;对象型/观测型更新语义。
- **P2 规模化**:每需求运行时设置覆盖;配额与调度优先级;画像市场。

### A.4 迁移与兼容

- 数据库:不改列名、不删列;沿用"ADD COLUMN 幂等迁移"。
- 老画像:缺任何新键都用缺省值,升级后不改画像也能跑。
- 配置文件位置不搬家;接口的 `need_id` 参数保留,默认值从 `settings.default_need_id` 取;新增 `GET /needs/{id}/ui`。
- 测试:既有 359 项全部保留;新增平台泛化测试集。

### A.5 风险与取舍

| 风险 | 处理 |
|---|---|
| 提示词参数化后质量波动 | 平台级通用硬规则固定在引擎;画像只追加领域规则,不能删除通用规则 |
| 画像键太多,新需求填不动 | 必填只有少数几项;其余全有缺省;v1.5 起共性参数从参数库 `use` |
