## 1. 多视角复查

> 本章在动手前从不同视角把方案压一遍:合理吗、落得了地吗、提炼的共性真的是共性吗、维度够不够、够不够灵活、够不够细。

### 视角一:新需求作者(要上线下一个任务的人)

- **要写多少东西?** 任务模式下:一份任务文件(元信息 + 节奏 + 几个 `use` + 粗筛目标/合规/对标),典型十几行 + 几个引用;词表/关键词/找源配方/种子/Schema 全部可省。判定:**通过**(v1.5 后比 v1.1 的"9 项必填 + 4 个文件"再降一档)。
- **填错了会怎样?** 引用不存在的条目直接报错;六要素缺项拒绝激活;未知键目前只走缺省。判定:**需修正(P1)**——画像本身要有 JSON Schema 校验。
- **字段角色不够用怎么办?** 标准角色 15 个;招标库 subject=采购人、dim1=采购品类、grade=金额档、tags_a=中标供应商;不够用 `dim2/region2/tags_b` 兜底。判定:**通过**。

### 视角二:引擎维护者

- **改 14 个模块会不会把首个实例改坏?** 每个模块只做"取参来源替换",缺省值 = 原行为;既有测试全部保留作回归护栏。判定:**通过**。
- **提示词参数化后,通用硬规则会不会被任务删掉?** 平台通用规则固定在引擎,任务只能追加。判定:**通过**。
- **没有 db 会话怎么取画像?** 缓存 → 库 → 画像文件 → 任务文件编译 → 中性缺省。判定:**通过**。

### 视角三:数据质量与合规

- **发布红线会不会因参数化变松?** 三要素(确认断言必须挂允许等级、含确认断言必双签、追溯闸门)全部保留,等级列表读画像;政策类 `confirm_allowed=[S1]` 更严。判定:**通过**。
- **三态守卫泛化后还认得出"赎金≠损失"吗?** 隔离规则 `isolation: [{source_path, must_not_match}]`,首个实例声明赎金;招标类可声明"预算金额≠中标金额"。判定:**通过**,比原来更通用。
- **合规段只是声明?** 是,`compliance` 不驱动行为。判定:**明确不做(P0)**,P1 考虑 `personal_info=true` 强制最小化与审计。

### 视角四:运维与部署

- **多任务并行时启动/调度怎么跑?** 启动注册全部画像与任务;每日采集与自动运维对每个"激活且可跑"的任务各跑一轮;暂停/结束的任务不进自动化。判定:**通过**。
- **一源多任务时可信度冲突?** `Source.credibility` 是源属性;任务级差异靠主体信誉名录重定级。判定:**通过**。
- **数据库迁移?** 不改列、不删列,沿用 ADD COLUMN 幂等迁移。判定:**通过**。

### 视角五:使用者(前端)

- **切任务后界面会不会还是"事件/线索/严重度"?** 页签、列名、筛选、详情、仪表盘卡片全部由 `/needs/{id}/ui` 驱动。判定:**通过**。
- **遗留物理列名会不会暴露?** 接口返回角色名 + 标签;前端只认角色。判定:**通过**。

### 视角六:跨原型压测(记录四型)

| 维度 | 事件型(安全) | 文档型(政策) | 对象型(招标) | 观测型(企业动态) | 结论 |
|---|---|---|---|---|---|
| 去重键 | 主体∩类型±14d | 文号精确 | 项目编号 | 企业+标题 30 天 | 通过;对象型 diff/追加语义 P1 |
| 记录类型 | 单一/通报/不该 | 正式/征求/不该 | 招标/中标/变更/废标 | 动态/汇总/不该 | 通过(值集自由) |
| 回访 | 金额落地 | 状态跃迁 | 待公布中标人 | 少量 | 通过;观测型可 `followup_schedule: []` |
| 线索 | 开 | 关 | 关 | 关 | 通过 |
| 报表 | 4 种 | 交叉+缺字段 | 数值金额汇总+缺字段 | 交叉 | 时间序列报表 P1 |
| 三态 | 金额 | 无 | 无(数值) | 无 | 通过(空即空转) |

### 视角七:提炼维度的共性/充分性/灵活性/粒度

- **共性**:引擎里剩下的常量只有五类(搜索引擎跳转域、通用大平台域、备案页脚域、跟踪参数、平台号识别),对任何中文互联网需求都成立。判定:**通过**。
- **充分性**:03 附录 A 的 H1–H24 每一项都有对应画像键(02 §3)。判定:**通过**。
- **灵活性**:同一维度允许"整体替换"(screen 整段)与"局部追加"(extract_rules);任务模式下列表追加、标量覆盖。判定:**通过**。
- **粒度**:最细到单条正则、单条回访触发、单条话术;最粗到整段关闭(`leads_engine.enabled=false`)或整个记录形态条目。判定:**通过**。
- **发现的缺口**(P1):画像 Schema 校验、时间序列报表、对象型 diff、告警输出、合规驱动行为。

### 视角八:可落地性

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| 无回归 | 既有测试 | 全绿 |
| 零行业字面量 | AST 扫描 `app/services`、`app/api`、cli、main | 扫描通过 |
| 第二需求真跑引擎 | 政策库全链:注册 → 粗筛 → 抽取 → 闸门 → 去重(文号)→ 草稿(POL、发布机关、主题)→ 红线(仅 S1)→ 回访 → 日报 | 全链断言通过 |
| 参数替换生效 | 同一段引擎在两个任务下输出不同 | 断言通过 |
| 多任务运行 | 启动注册多画像/任务;自动运维按任务循环;`GET /needs` 列全 | 断言通过 |

### 视角九:需求泛化

- **例子之外的需求都能表达吗?** 六根轴(05 §1),任何需求是轴上取值的组合;生成式测试按轴组合自动生成 13 份画像并跑通链路。判定:**通过**。
- 仍要人做的:范围词的同义/别名(可让模型扩、可从参数库复用)、来源种子(可全靠找源)、Schema(可轻量)。

### 视角十:模块独立与升级

- 三层、只向下依赖、能力层无环、服务层不引接口层,全部有测试守护;能力统一签名进注册表;新增画像维度只加中性缺省不改旧画像(07)。判定:**通过**。

### 视角十一:任务模式(v1.5)

- **任务和画像会不会两套真理?** 不会:引擎只认画像;任务是画像的"人写形态",编译产物入库;手写画像 = 无引用的任务。判定:**通过**。
- **参数库条目改了,已装载的任务会自动变吗?** 不会自动变——编译发生在装载时;重新 `task-setup` 才生效,这是有意的(运行中的任务不被库改动意外影响);`library-list` 的 `used_by` 告诉你要重装哪些。判定:**通过**,P1 考虑"库变更影响面提示"。
- **列表只能追加不能删除,会不会限制?** 会,但换来"条目叠加可预测";需要替换就不引用该条目。判定:**通过**(已在 01 §4.2 写明)。
- **转换后的五个任务和原手写画像等价吗?** 转换脚本逐段对照(允许 need 的 owner/priority/timeliness_sla 由 task 映射),全部等价;测试持续守护。判定:**通过**。

## 4. 已知边界

- 物理查询列仍是首个实例时代的列名(`industry_l1/org_name/severity/...`),语义由 `ROLE_COLUMNS` 决定;新增第 3 个维度或第 3 组标签需要加列。
- 每日自动化按任务串行;多任务并发调度、告警型/订阅型输出按 P2 排期。
- 参数库条目变更不自动重编译已装载任务(有意);影响面提示 P1。
- `compliance` 段不驱动行为;画像 JSON Schema 校验 P1。
- 前端"设置""数据源""采集"三页与领域无关;"回访/复核台/线索"页文案沿用平台词,页签名可由任务改。
