# 通用数据采集平台 · 多视角验证(v1.0)

> 目的:在动手前从不同视角把方案压一遍——合理吗、落得了地吗、提炼的共性真的是共性吗、
> 个性维度够不够、够不够灵活、够不够细。每条结论都给出"通过 / 需修正 / 明确不做"的判定。

---

## 视角一:新需求作者(要上线第三个需求的人)

**问题:我到底要写多少东西?** 最小画像 9 项必填 + 1 份 JSON Schema + 1 份词表 + 1 份关键词矩阵 + 1 份种子源。
其余 43 项全有缺省。招标情报库的作者按 02 §3 对照表逐行填即可,不需要读引擎代码。

**问题:填错了会怎样?** 目前只校验六要素齐备(`profiles.validate_profile`)。
- 判定:**需修正(P1)**——画像本身要有 JSON Schema 校验,键名打错应当立即报错而不是静默走缺省。P0 先在 `NeedContext` 里对未知顶层键打印警告。

**问题:字段角色不够用怎么办?** 标准角色 15 个,覆盖"主体/分类/地区/等级/两组标签/两个日期/记录类型"。
招标库:subject=采购人,dim1=采购品类,grade=金额档,tags_a=中标供应商;舆情库:subject=账号,dim1=话题,grade=情感,tags_a=平台。
- 判定:**通过**。角色不够时用 `dim2/region2/tags_b` 兜底;确需更多查询列走 P1 通用列迁移。

## 视角二:引擎维护者

**问题:改 14 个模块会不会把 sec_events 改坏?** 每个模块只做"取参来源替换",缺省值 = 今天的值;
既有 359 项测试全部保留作回归护栏。
- 判定:**通过**,前提是测试全绿。

**问题:提示词参数化后,通用硬规则会不会被画像删掉?** 平台通用规则(不臆造/未披露用 status/附原文片段/日期精度/来源 url 真实)固定在引擎,画像只能**追加**领域规则。
- 判定:**通过**。

**问题:`_sync_columns` 没有 db 会话怎么取画像?** 用 `object_session(ev)` 取会话;取不到再按文件找画像;再取不到用中性缺省。
- 判定:**通过**。

## 视角三:数据质量与合规

**问题:发布红线会不会因为参数化而变松?** 红线三要素——确认断言必须挂 `confirm_allowed` 等级、含确认断言必双签、追溯闸门——全部保留,只是等级列表改读画像。政策库 `confirm_allowed=[S1]` 比安全库更严。
- 判定:**通过**。

**问题:断言三态守卫泛化后还认得出"赎金≠损失"吗?** 隔离规则变成 `isolation: [{source_path, must_not_match: tristate}]`,安全库声明赎金;其他需求可声明自己的(如招标库"预算金额≠中标金额")。
- 判定:**通过**,且比原来更通用。

**问题:合规画像只是声明?** 是。`compliance` 段目前不驱动任何行为。
- 判定:**明确不做(P0)**,列入 P1:`personal_info=true` 时强制最小化字段与审计。

## 视角四:运维与部署

**问题:多需求并行时启动/调度怎么跑?** 启动时按 `need_profile_glob` 注册全部画像并各自幂等载入种子;自动运维与每日采集对**每个激活需求**各跑一轮;首次部署流程按需求分别执行。
- 判定:**通过**。

**问题:一源多需求时可信度冲突?** `Source.credibility` 是源属性;需求级差异靠主体信誉名录重定级(已有)。
- 判定:**通过**。

**问题:数据库迁移?** 不改列、不删列,沿用 ADD COLUMN 幂等迁移。
- 判定:**通过**。

## 视角五:使用者(前端)

**问题:切需求后界面会不会还是"事件/线索/严重度"?** 页签、列名、筛选、详情面板、仪表盘卡片全部由 `GET /needs/{id}/ui` 驱动;详情面板用通用渲染器(kv/tags/tristate/object/list/text/sources)。
- 判定:**通过**。

**问题:遗留物理列名会不会暴露给用户?** 接口返回角色名 + 标签;前端只认角色。
- 判定:**通过**。

## 视角七:提炼维度的共性/充分性/灵活性/粒度

- **共性**:引擎里剩下的常量只有五类——搜索引擎跳转域、通用大平台域、备案页脚域、跟踪参数、平台号识别。它们对任何中文互联网需求都成立,不属于某个行业。判定:**通过**。
- **充分性**:对照 01 §0 的 H1–H24,每一项都有对应的画像键(02 §2)。唯一未参数化的是 `SEARCH_REDIRECT_HOSTS` 这类平台常量与角色→物理列映射。判定:**通过**。
- **灵活性**:同一维度允许"整体替换"(如 screen 整段)与"局部追加"(如 extract_rules)两种粒度;找源配方、评分、定级可以按需求换文件。判定:**通过**。
- **粒度**:最细到单条正则(scope_guard)、单条回访触发、单条线索话术;最粗到整段关闭(leads_engine.enabled=false)。判定:**通过**。
- **发现的缺口**(已在 02 标注 P1):画像 Schema 校验、时间序列报表、对象型 diff、告警输出、合规驱动行为。

## 视角八:可落地性与验证方式

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| 无回归 | 既有 359 项测试 | 全绿 |
| 零行业字面量 | 测试扫描 `app/services`、`app/api`:不得出现画像里的领域词(勒索/网警/loss_L/医院…) | 扫描通过 |
| 第二需求真跑引擎 | 政策库:注册 → 粗筛 → 抽取(Mock 按 Schema 骨架 + 画像规则)→ 范畴闸门 → 记录去重(文号)→ 草稿(POL- 前缀、subject=发布机关、dim1=主题)→ 发布红线(仅 S1)→ 回访触发(状态未落定)→ 日报标题 | 全链断言通过 |
| 参数替换生效 | 同一段引擎在两个需求下输出不同(提示词含各自规则、自检词不同、覆盖维度不同、线索开关不同) | 断言通过 |
| 多需求运行 | 启动注册两个画像;自动运维按需求循环;`GET /needs` 列出两个 | 断言通过 |


## 视角九:需求泛化(v1.2 补)
- 问:例子之外的需求(某省某类文件、某厅局要求、某企业动态、招标中标…)是不是都能表达?
- 答:把需求空间拆成 W 对象 / S 范围 / F 来源 / D 深度 / L 生命周期 / O 输出 六根轴(07),任何需求是轴上取值的组合;
  画像按轴填值。用生成式测试(按轴组合自动生成 13 份画像并跑通链路)证明,而不是靠手写例子。
- 仍要人做的:范围词的同义/别名(可让模型扩)、来源种子(可全靠找源)、Schema(可用轻量模式省掉)。

## 视角十:模块独立与升级(v1.2 补)
- 问:改一个模块会不会牵一发动全身?
- 答:三层、只向下依赖、能力层无环、服务层不引接口层,全部有测试守护;能力统一签名进注册表,
  流水线阶段/运维任务/接口/CLI 都按名字调用;新增画像维度只加中性缺省不改旧画像(08)。
- 本次按此标准清掉了 6 处跨层/环状引用(08 §5)。
