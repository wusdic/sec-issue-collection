# 通用数据采集平台 · 实施方案(v1.0)

> 目标:把「国内行业安全事件库」这套已跑通的系统提炼为**与领域无关的数据采集平台**。
> 一切行业个性(要采什么、用什么词找、谁可信、什么算确认、怎么回访、怎么出报表、界面叫什么)
> 全部下沉为**需求画像(need profile)参数**;引擎代码不再出现任何行业字面量。
> 判定标准只有一条:**新增一个信息需求 = 写一份画像 + 一份 Schema + 几份词表,零改代码。**

## 1. 设计原则

1. **引擎零行业字面量**:`app/services` 与 `app/api` 里不允许出现任何具体行业/地域/产品词;
   出现即视为缺陷。词、规则、阈值、文案一律来自画像或平台级(与领域无关的)常量。
2. **画像即契约**:画像 YAML 是唯一的个性来源。每个参数维度都有:键名、类型、缺省值、消费方、
   缺省时的行为。缺省值 = 今天 sec_events 的行为,保证**老画像不改也能跑**(向后兼容)。
3. **平台常量 vs 需求参数**分清楚:
   - 平台常量(与领域无关,所有需求共享):搜索引擎跳转域、通用大平台域、备案页脚域、
     跟踪参数、多段公共后缀、平台号识别(公众号/百家号/微博)、翻页/早停/反爬/渲染策略;
   - 需求参数(随需求变):后文《02-业务逻辑与参数化维度》的全部 8 组 52 项。
4. **角色化而非改名**:数据库里的查询列(`industry_l1/severity/attack_types/...`)物理名不改
   (避免破坏性迁移),但语义由画像的 `field_roles` 决定——同一列在政策库里装的是 `topics`。
   接口同时返回物理名与角色名;后续可平滑迁移为 `dim1/dim2/grade/tags_a` 等通用名。
5. **一处解析,处处复用**:新增 `services/need_ctx.py`,把画像解析成带缺省值的 `NeedContext`
   对象(按 need_id + 配置哈希缓存);所有模块只从它取参数,禁止各自去读 YAML。
6. **可验证**:泛化成不成立,用第二需求(政策库)跑完整引擎来证明,而不是靠文档宣称。

## 1.6 v1.2 追加的两条原则

- **范围先于字段**:需求先说清"要哪一片"(地域/行业/主题/主体/文种/时间窗),再说"记录长什么样"。
  范围一处声明(`scope`),关键词、粗筛、闸门、覆盖度、找源都从它取,不允许各处各写一份。
- **能力即模块,组合靠声明**:底层能力统一签名登记进注册表,流水线阶段、自动运维任务、接口、CLI 都是
  "按名字调用";画像用 `pipeline.stages` 声明顺序。升级一个能力不碰别的模块(分层与依赖方向有测试守护,见 08)。

## 2. 目标架构

```
┌──────────────────── 需求画像层(每需求一份,纯数据) ────────────────────┐
│ need_<id>.yaml  ─→  Schema(JSON)  词表(YAML)  关键词矩阵  找源配方   │
│                     种子源  主体信誉名录  产品映射  报表/线索/界面定义   │
└─────────────────────────────┬──────────────────────────────────────────┘
                              │ profiles.load → NeedContext(带缺省,缓存)
┌─────────────────────────────▼──────────────────────────────────────────┐
│ 通用引擎(零行业字面量)                                                  │
│  源层:种子/发现(D1–D6)/找源(G2)/栏目定位/体检/定级/自动运维/首次流程     │
│  采集层:适配器(RSS/列表/搜索/平台号)/渲染/反爬/翻页早停/时效/存档        │
│  处理层:三层去重 → 粗筛(画像规则) → 抽取(Schema+画像规则) → 断言守卫    │
│          → 记录去重(画像键) → 草稿 → 复核双签 → 发布红线(画像等级)      │
│  更新层:生命周期/回访(画像触发)/名单监控/对标                          │
│  输出层:线索(画像映射与权重)/报表(画像口径)/日报(画像分组)/动作台账     │
│  界面层:需求选择器 + 由画像 ui 段驱动的页签/列名/详情面板               │
│  (v1.2)范围限定 scope → 关键词生成/粗筛/闸门/覆盖/找源;阶段可组合;能力注册表 │
└────────────────────────────────────────────────────────────────────────┘
分层:L0 契约与底座(need_ctx/prompts/llm/fetcher/…)← L1 能力模块 ← L2 编排 ← 接口/CLI/前端;
只向下依赖、能力层不成环(tests/test_module_boundaries.py),详见 08。
┌──────────────────── 平台常量(与领域无关,所有需求共享) ──────────────────┐
│ 搜索引擎池/跳转域/大平台域/页脚域/跟踪参数/公共后缀/平台号识别/反爬策略 │
└────────────────────────────────────────────────────────────────────────┘
```

多需求并行:`NeedProfile` 表已有;`Source.serves_needs` 已支持一源多需求;
所有带 `need_id` 的表已隔离。缺的是**调度/启动/首次流程按"全部激活需求"循环**,
以及**默认需求**从 40 处字面量收敛到 `settings.default_need_id` 一处。

## 3. 实施分期

### P0 · 契约与骨架(本次交付 · **已完成,见 05-落地验证**)
- `NeedContext`:52 项参数的解析 + 缺省 + 缓存;
- `need_sec_events.yaml` 显式写全 52 项(把代码里的值搬进画像);
- `need_policy_watch.yaml` 写全,作为**跨原型(文档型)**的验证实例;
- 引擎 14 个模块改为从 `NeedContext` 取参(H1–H20 销号);
- 默认需求收敛 + 启动/自动运维/首次流程按全部需求循环(H21);
- 前端:需求选择器、页签/列名/详情面板由画像 `ui` 段驱动(H22);
- 演示数据进画像(H23);声明未消费项接线或标注(H24);
- Mock 模型改为 Schema 驱动的通用骨架(H20);
- 验证:政策库跑通 采集→粗筛→抽取→去重→草稿→发布 全链;全部既有测试不回归。

### P1 · 平台化补强(下一步)
- 画像的 JSON Schema 校验(画像本身也有 Schema,填错立即报错);
- 画像热加载与版本化(改画像不重启;记录哪一版画像产生了哪条记录);
- 通用查询列迁移为 `dim1/dim2/region/subject/grade/tags_a/tags_b`(带 Alembic);
- 告警型输出(`outputs.alerts`)与订阅型输出落地;
- 对象型/观测型两种记录原型的更新语义(diff / 追加观测点)。

### P2 · 规模化
- 每需求独立的运行时设置覆盖(并发/阈值按需求);
- 需求级配额与调度优先级(SLA 反向驱动已在,补跨需求争用仲裁);
- 画像市场:内置更多行业模板(招标情报/舆情/竞品)。

## 4. 迁移与兼容

- **数据库**:不改列名、不删列;仅沿用现有"ADD COLUMN 幂等迁移"机制。
- **老画像**:缺任何新键都用缺省值(= sec_events 今天的行为),因此升级后不改画像也能跑。
- **配置文件位置**:不搬家。画像里已用相对路径声明各文件,新增声明沿用同一方式。
- **接口**:所有路由的 `need_id` 参数保留,默认值从 `settings.default_need_id` 取;
  新增 `GET /needs/{id}/ui` 供前端拿页签/列名/详情面板定义。
- **测试**:既有 359 项全部保留;新增《平台泛化》测试集专门证明第二需求走完引擎。

## 5. 风险与取舍

| 风险 | 处理 |
|---|---|
| 提示词参数化后质量波动 | 平台级"通用硬规则"(不臆造/未披露用 status/附原文片段/日期精度)固定在引擎;画像只追加领域规则,不能删除通用规则 |
| 画像键太多,新需求填不动 | 52 项里**必填只有 9 项**(见 02 文档"最小画像"),其余全有缺省;提供模板与政策库两份范例 |
| 反规范化列语义混用 | 接口同时返回 `role` 名;前端只认角色名;文档明确物理列为遗留别名 |
| Mock 模型泛化后现有测试断言变化 | Mock 仍按"关键词命中→相关、Schema 必填→骨架"产出;sec 特有的赎金抽取保留为**画像 demo 规则**,不是引擎逻辑 |
| 一次改 14 个模块的回归风险 | 每模块改动最小化为"取参来源替换";全量测试 + 新增泛化测试双保险 |
