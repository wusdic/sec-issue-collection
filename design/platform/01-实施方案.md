# 通用数据采集平台 · 架构设计与实施方案(v1.3,模块式分层架构)

> 本文回答"平台是怎么搭的、每一层承担什么需求、为什么这样分、怎么在不动别人的前提下改一层"。
> 主线目标见 00 总纲;参数见 02;每个功能的用法见 03;模块契约与升级规范见 08。
> 原 v1.1 的现状审计与分期记录保留在附录 A。

## 0. 架构总览

```
┌─ 界面层 ─────────────────────────────────────────────────────────────────────┐
│ 单页管理台(需求切换 / 仪表盘 / 记录 / 复核台 / 回访 / 线索 / 数据源 / 采集 / 动作 / 日报 / 设置)   │
│ 只认 /needs/{id}/ui 给出的角色与定义,不认任何行业字段                                           │
├─ 接口层 ─────────────────────────────────────────────────────────────────────┤
│ REST(/api/v1,JWT + 角色)· CLI(python -m app.cli)· 能力调用(/capabilities/{name}/run)         │
├─ 编排层 L2 ──────────────────────────────────────────────────────────────────┤
│ pipeline(采集入库 + 阶段化处理)· prospect(主动找源)· scheduler / crawl_runner(采集任务)        │
│ autopilot(自动运维 9 任务)· bootstrap(首次流程 8 步)· daily(每日调度)· profiles(需求装载)      │
│ capabilities(能力注册表)· locate(批量栏目定位)                                                   │
├─ 能力层 L1 ──────────────────────────────────────────────────────────────────┤
│ 采集:adapters(源适配器注册表)columns health wechat                                              │
│ 处理:extraction money_guard dedup events review verify relations                                │
│ 关键词/找源:keywords discovery grading query_evolution                                          │
│ 更新/输出:followup leads kpi digest coverage exports                                             │
├─ 底座与契约层 L0 ────────────────────────────────────────────────────────────┤
│ 契约:need_ctx(画像 → 参数对象,角色↔列)prompts(提示词)                                         │
│ 底座:llm(模型客户端/离线 Mock)fetcher(抓取/渲染)archive(当刻存档)url_tools simhash               │
│       reputation(主体信誉)settings_service(运行时设置)actions(动作台账)notify(通知组件)diagnostics │
├─ 数据与存储层 ───────────────────────────────────────────────────────────────┤
│ SQLAlchemy 模型(SQLite 开发 / PostgreSQL 生产)· 存档目录(ARCHIVE_ROOT)· 本地资料库目录          │
├─ 配置层(纯数据,每需求一份)──────────────────────────────────────────────────┤
│ need_<id>.yaml(画像)· Schema(JSON)· 词表 · 关键词矩阵 · 找源配方 · 种子源 · 信誉名录 · 产品映射    │
│ 运行时设置(.env + 设置页,库表 app_setting)                                                        │
└──────────────────────────────────────────────────────────────────────────────┘
依赖方向:上层 → 下层;同层(L1)不成环;服务层不引接口层;引擎代码零行业字面量。三条规则都有测试守护。
```

**为什么是这个分法**:平台要同时满足两类相互拉扯的需求——"不同需求差异极大"(法规/招标/企业动态/事件)与
"引擎改一处不能牵动全局"。把**差异全部压进配置层**,由**契约层**翻译成统一参数对象,**能力层**每个模块只做一件事
且只从契约层取参,**编排层**只负责按名字把能力串起来,界面层只认角色。改画像不碰代码,改能力不碰编排,加渠道
不碰主线。

## 1. 各层的需求与设计要求

每层按同一格式说明:承担的需求 → 职责边界 → 输入/输出 → 质量要求 → 依赖与扩展规则 → 禁止事项 → 包含模块 → 验证方式。

### 1.1 配置层(需求画像与配套文件)

- **承担的需求**:让"新需求"只是一份 YAML;让不会写代码的需求负责人能表达"要什么范围、记录长什么样、怎么算真、怎么输出"。
- **职责边界**:只放数据,不放逻辑;画像可省略任何非必填键(中性缺省);配套文件全部可省(关键词/找源配方按 scope 生成、Schema 可用轻量模式)。
- **输入/输出**:人写画像 → `profiles.setup_need` 装载进库(NeedProfile + 词表 + 关键词 + 种子源)。
- **质量要求**:9 个必填键即可上线;六要素与覆盖基准校验(缺项拒绝激活);画像变更可增量(老画像不改照常跑);模板与文档同步。
- **依赖与扩展**:新增维度 = `need_ctx.DEFAULTS` 加中性缺省 + 02 文档登记;模板 `config/need_profile.template.yaml` 是唯一权威样板。
- **禁止**:在画像里写代码或路径以外的行为;在引擎里出现画像里的具体取值。
- **包含**:`config/need_*.yaml`、`schema/*.json`、`schema/*_dictionaries.yaml`、`config/keyword_matrix*.yaml`、`config/discovery*.yaml`、`config/seed_sources*.yaml`、`config/*_accounts.yaml`、`config/product_mapping.yaml`。
- **验证**:`test_platform_generalization`(两画像)、`test_scenarios`(四画像)、`test_demand_matrix`(生成式 13 组合)。

### 1.2 契约层(need_ctx / prompts)

- **承担的需求**:全平台唯一的取参入口;把画像的"意图"翻译成引擎能直接用的参数、角色、提示词;保证没有画像也有中性行为。
- **职责边界**:解析/合并/缺省/缓存;角色 → payload 路径 → 物理列三级映射;轻量 Schema 生成;界面定义 `to_ui()`;显式 null 语义;地域策略推导;Schema 文件加载与缓存。提示词只由画像与 scope 组装,含 `NEED_ID`/`SCHEMA_FILE` 标记供离线 Mock 对齐。
- **输入/输出**:`get(db, need_id)` / `for_need(np)` / `from_config(cfg)` → `NeedContext`;无会话时优先本进程缓存,再查库,再读文件,再中性缺省。
- **质量要求**:纯函数式(除缓存),毫秒级;线程安全;同一需求同一配置只构造一次;任何键缺失都不抛。
- **依赖与扩展**:只依赖 `config`/`settings`;**不得**引用能力层(有测试)。新角色 = `ROLE_COLUMNS` + 列;新参数 = `DEFAULTS`。
- **禁止**:读库外文件以外的 I/O;出现行业字面量;反向依赖能力层。
- **验证**:`test_module_boundaries::test_contract_layer_only_depends_on_itself`、字面量扫描。

### 1.3 底座层(llm / fetcher / archive / url_tools / simhash / reputation / settings_service / actions / notify / diagnostics)

- **承担的需求**:与领域无关的"硬能力":调模型、抓网页(含渲染/反爬/编码)、存档、URL 归一/跳转还原/平台号识别、同稿哈希、主体信誉、运行时设置、动作台账、通知渠道、诊断留痕。
- **职责边界**:每个底座模块只解决一类技术问题;不知道"记录"是什么;不读画像(通知组件例外:只读 `outputs.notify.channels`)。
- **输入/输出**:字节/URL/文本进,结构化结果出(`FetchResult`、`ArchiveManifest`、向量、归一化键、`(ok, note)`)。
- **质量要求**:可靠优先——超时/重试/降级链(渲染→httpx;存档 L-A→L-D);编码正确(头 → meta → 猜);限速与退避;离线可用(Mock 模型、无 Playwright 自动降级)。
- **依赖与扩展**:只依赖同层;新模型供应商 = `llm._build` 分支;新通知渠道 = `notify.CHANNELS` 登记;新反爬策略进 `fetcher`。
- **禁止**:依赖能力层/编排层;写业务规则。
- **验证**:`test_fetcher*`、`test_archive*`、`test_llm_compat`、`test_notify_and_library`。

### 1.4 能力层 L1(独立可调的功能模块)

- **承担的需求**:主线五目标的每一步都是一个可单独调用、可单独升级的模块(找源、关键词、粗筛、抽取、守卫、去重、验证、关系、回访、线索、报表、日报、覆盖、导出、体检、栏目、定级、词进化)。
- **职责边界**:一个模块一件事;公开函数签名稳定;`ctx` 参数可省(缺省=默认需求);同层只能用彼此的公开函数且不成环。
- **输入/输出**:见 08 §2 的契约表;统一都能通过 `capabilities.run(name, db, need_id, **params)` 调用。
- **质量要求**:确定性(同输入同输出,便于回放);容错(模型异常/网络异常不抛到编排层,返回可解释结果);可观测(每步 `diagnostics.record`)。
- **依赖与扩展**:依赖 L0 与同层公开函数;新增能力 = 新模块 + `capabilities.register`;新增阶段 = 阶段函数 + `pipeline.STAGES`。
- **禁止**:引用编排层;跨模块用私有函数(`_x`);出现行业字面量;自行读画像文件。
- **验证**:`test_module_boundaries`(无环、不向上)、各模块单测、`test_scenarios`/`test_demand_matrix`(跨需求)。

### 1.5 编排层 L2(把能力串成流程)

- **承担的需求**:采集一篇文档的完整链路、主动找源一轮、每日/自动运维/首次部署流程、需求装载;把"人不该按的按钮"变成到点自动跑。
- **职责边界**:只做顺序、并发、预算、状态落库与错误隔离;业务判断都在能力层。流水线阶段顺序由画像 `pipeline.stages` 决定。
- **输入/输出**:任务参数进,`AutoOpsRun`/`CrawlJob`/`CrawlRun` 等运行记录出;进度可查、可取消、切页不丢。
- **质量要求**:幂等(种子载入、候选入库、日报 upsert);时间预算而非条数上限;单步失败不拦后续;SQLite 写锁友好(网络 I/O 前先提交);并发取号不撞主键。
- **依赖与扩展**:可依赖任何下层;新自动运维任务 = `autopilot.TASKS` 加一项;新首次流程步骤 = `bootstrap.STEPS`。
- **禁止**:写业务规则;直接读画像文件;引用接口层。
- **验证**:`test_autopilot_grading`、`test_bootstrap`、`test_crawl_job`、`test_parallel_crawl`、`test_concurrency`。

### 1.6 接口层(REST / CLI / 能力调用)

- **承担的需求**:给界面、外部程序、运维脚本一个稳定入口;所有 `need_id` 缺省为平台默认需求;鉴权与角色。
- **职责边界**:参数校验、鉴权、调用编排层/能力层、审计日志;不含业务逻辑(试抓等已下沉到服务层)。
- **输入/输出**:JSON;错误用 HTTP 状态 + 中文 detail。
- **质量要求**:每个接口一个明确角色要求(admin / analyst / editor / reviewer / readonly);长任务全部异步 + 状态接口;接口对行业无感(角色键)。
- **依赖与扩展**:新接口只包一层服务函数;能力型功能优先走 `/capabilities/{name}/run` 而不是新增接口。
- **禁止**:服务层反向引用;在接口里写行业字面量。
- **验证**:`test_platform_generalization::test_needs_api_and_ui`、各接口用例、双需求 HTTP 冒烟(05 §2.2)。

### 1.7 界面层(单页管理台)

- **承担的需求**:让运营/分析/复核人员不看代码就能用;换需求不换界面。
- **职责边界**:启动拉 `/needs` + `/needs/{id}/ui`,页签/列/筛选/详情分区/仪表盘卡片/日报文案全部按定义渲染;数据源页按"自动化优先"排布(动作按钮收起,只留需要人拍板的)。
- **质量要求**:切页不丢后台任务状态(状态在服务端);每个数字有说明;错误可读。
- **依赖与扩展**:只认角色与 UI 定义;新页签需要后端 `to_ui()` 与前端一处路由。
- **禁止**:写死行业字段名、需求 id、页签名。

### 1.8 数据与存储层

- **承担的需求**:多需求隔离、可追溯、可回放、可迁移(SQLite ↔ PostgreSQL)。
- **职责边界**:35 张表分七组——需求与用户(need_profile / app_user / app_setting / audit_log)、源(source / source_metric_daily / source_discovery_evidence / source_probe / source_blacklist / keyword_set / keyword_run / search_query_stat / term_stat / watch_target / search_watermark)、采集(crawl_job / crawl_run / crawl_log / run_trace / raw_document / doc_cluster / archive_manifest)、记录(event / event_source / event_change_log / record_relation / review_task / dictionary_release)、更新与输出(followup_task / lead / daily_digest / benchmark_batch / benchmark_item)、运维(action_log / auto_ops_run)。
- **质量要求**:所有业务表带 `need_id`;查询列由角色映射(语义在画像);轻量列迁移(`_ADDED_COLUMNS`,只加不改);存档文件带 manifest 哈希可抽检。
- **禁止**:在表名/列名之外新增行业语义;跨需求共享记录。

### 1.9 运行与部署层

- 单进程可跑全部(FastAPI + 进程内调度线程 + 后台任务线程);可选 Celery/Redis 与 PostgreSQL;Playwright 可选(没有自动降级);LLM 供应商可换(OpenAI 兼容接口、离线 Mock);全部参数 `.env` + 设置页(库表)双通道,设置页改即时生效。
- 安全与合规:只采公开渠道;泄露站只登记元数据与截图;密级标记文档只登记不入库正文;JWT + 角色;审计日志;不贬损任何主体(线索话术规则)。

## 2. 贯穿各层的四个注册表(扩展点)

| 注册表 | 位置 | 登记什么 | 谁来消费 |
|---|---|---|---|
| 源适配器 `adapters._REGISTRY` | L1 | `name` → 适配器类(json_api / generic_rss / generic_list / 搜索引擎 / 公众号 / 微博 / 专用站) | 种子源、找源、体检、试抓 |
| 流水线阶段 `pipeline.STAGES` | L2 | 阶段名 → `fn(db, need, ctx, doc, st, result) -> bool` | 画像 `pipeline.stages` |
| 能力 `capabilities._REG` | L2 | 能力名 → `fn(db, ctx, **params)` + 说明/参数 | REST `/capabilities`、CLI `cap-run`、前端 |
| 通知渠道 `notify.CHANNELS` | L0 | 渠道名 → `fn(subject, body, cfg)` | 日报、告警、能力 `notify.send` |

## 3. 典型调用序列

**A. 采集一篇文档(每日自动)**
`daily._tick` → `crawl_runner.start_job` → `pipeline.crawl_source`(适配器发现 → `ingest_item`:跳转还原 → URL 去重 → 时效窗 → 抓取/编码 → 同稿簇 → 引文/转载登记 → 存档)→ `process_document` 按 `pipeline.stages`:screen → verify → extract(+guard)→ scope_gate → content_check → dedup_record → [relations] → draft → `ReviewTask` → 复核发布 → `followup.schedule` / `leads.generate` / `relations.link` → 日报 → 通知组件 → 导出组件(本地资料库)。

**B. 首次部署**
`bootstrap.start`:precheck(模型/渲染/引擎)→ seeds → engines(自检并只留可用)→ dedup → locate(根域源定位栏目)→ health → crawl(第一轮)→ prospect(此时覆盖空白与语料都有了)。

**C. 新增需求**
复制模板 → 填 9 个必填键 + scope → `init --need <id>`(注册 + 词表 + 关键词自动生成 + 种子源)→ 界面切换需求 → 一键演示 → bootstrap。

| H18 | 追溯闸门 `{"S1","S2"}` 字面量(未用画像的 confirm_allowed) | `kpi.traceability_check` |
| H19 | 日报标题「安全事件日报」、分组维度(行业/严重度) | `digest.py` |
| H20 | 离线 Mock 模型的安全关键词与抽取骨架 | `llm.MockLLM` |
| H21 | 默认需求 `sec_events` 散落 40+ 处(路由默认参数/CLI/启动/调度/首次流程) | `routes/cli/main/daily/autopilot/bootstrap/celery` |
| H22 | 前端 `const NEED="sec_events"`、页签名(事件/销售线索)、列名(行业/严重度/手段)、详情面板(L1–L5/赎金/可售映射) | `web/index.html` |
| H23 | 演示数据(医院勒索/城商行 DDoS/车企泄露) | `routes.demo_seed` |
| H24 | 画像里**声明了但引擎没消费**的:`min_publish_fields`、`dedup_key`、`lagged_fields`、`followup_schedule`、`assertion_tristate_fields`、`double_review_fields`、`watch_kinds`、`expansion_rules`、`outputs.*`、`benchmark` | 需接线或明确标注"仅文档" |

**结论**:框架文档层面的泛化是对的,代码层面只做到了"多需求数据隔离",没做到"多需求共用引擎"。
现有的"泛化证据"测试 `test_need_isolation` 只断言了第二需求注册后事件数为 0,**没有让第二需求跑过任何一段引擎**。

### A.1. 设计原则

1. **引擎零行业字面量**:`app/services` 与 `app/api` 里不允许出现任何具体行业/地域/产品词;
   出现即视为缺陷。词、规则、阈值、文案一律来自画像或平台级(与领域无关的)常量。
2. **画像即契约**:画像 YAML 是唯一的个性来源。每个参数维度都有:键名、类型、缺省值、消费方、
   缺省时的行为。缺省值 = 今天 sec_events 的行为,保证**老画像不改也能跑**(向后兼容)。
3. **平台常量 vs 需求参数**分清楚:
   - 平台常量(与领域无关,所有需求共享):搜索引擎跳转域、通用大平台域、备案页脚域、
     跟踪参数、多段公共后缀、平台号识别(公众号/百家号/微博)、翻页/早停/反爬/渲染策略;
   - 需求参数(随需求变):后文《02-业务逻辑与参数化维度》的全部 8 组 52 项。
4. **角色化而非改名**:数据库里的查询列(`industry_l1/severity/attack_types/...`)物理名不改
   (避免破坏性迁移),但语义由画像的 `field_roles` 决定——同一列在政策库里装的是 `topics`。
   接口同时返回物理名与角色名;后续可平滑迁移为 `dim1/dim2/grade/tags_a` 等通用名。
5. **一处解析,处处复用**:新增 `services/need_ctx.py`,把画像解析成带缺省值的 `NeedContext`
   对象(按 need_id + 配置哈希缓存);所有模块只从它取参数,禁止各自去读 YAML。
6. **可验证**:泛化成不成立,用第二需求(政策库)跑完整引擎来证明,而不是靠文档宣称。

### A.1.5 主线与组件(v1.3)

平台主线是"针对一个信息需求:找得快、找得全、真实可信、好用可用、分类存本地"(见 00 总纲)。
通知(邮件/飞书/webhook)、导出(本地资料库/多维表格)、线索、日报是**功能组件**:可插拔、按画像声明启用、
不影响主线;新增渠道或导出目标只登记一个函数,不改引擎。

### A.1.6 v1.2 追加的两条原则

- **范围先于字段**:需求先说清"要哪一片"(地域/行业/主题/主体/文种/时间窗),再说"记录长什么样"。
  范围一处声明(`scope`),关键词、粗筛、闸门、覆盖度、找源都从它取,不允许各处各写一份。
- **能力即模块,组合靠声明**:底层能力统一签名登记进注册表,流水线阶段、自动运维任务、接口、CLI 都是
  "按名字调用";画像用 `pipeline.stages` 声明顺序。升级一个能力不碰别的模块(分层与依赖方向有测试守护,见 08)。

### A.2. 目标架构

```
┌──────────────────── 需求画像层(每需求一份,纯数据) ────────────────────┐
│ need_<id>.yaml  ─→  Schema(JSON)  词表(YAML)  关键词矩阵  找源配方   │
│                     种子源  主体信誉名录  产品映射  报表/线索/界面定义   │
└─────────────────────────────┬──────────────────────────────────────────┘
                              │ profiles.load → NeedContext(带缺省,缓存)
┌─────────────────────────────▼──────────────────────────────────────────┐
│ 通用引擎(零行业字面量)                                                  │
│  源层:种子/发现(D1–D6)/找源(G2)/栏目定位/体检/定级/自动运维/首次流程     │
│  采集层:适配器(RSS/列表/搜索/平台号)/渲染/反爬/翻页早停/时效/存档        │
│  处理层:三层去重 → 粗筛(画像规则) → 抽取(Schema+画像规则) → 断言守卫    │
│          → 记录去重(画像键) → 草稿 → 复核双签 → 发布红线(画像等级)      │
│  更新层:生命周期/回访(画像触发)/名单监控/对标                          │
│  输出层:线索(画像映射与权重)/报表(画像口径)/日报(画像分组)/动作台账     │
│  界面层:需求选择器 + 由画像 ui 段驱动的页签/列名/详情面板               │
│  (v1.2)范围限定 scope → 关键词生成/粗筛/闸门/覆盖/找源;阶段可组合;能力注册表 │
└────────────────────────────────────────────────────────────────────────┘
分层:L0 契约与底座(need_ctx/prompts/llm/fetcher/…)← L1 能力模块 ← L2 编排 ← 接口/CLI/前端;
只向下依赖、能力层不成环(tests/test_module_boundaries.py),详见 08。
┌──────────────────── 平台常量(与领域无关,所有需求共享) ──────────────────┐
│ 搜索引擎池/跳转域/大平台域/页脚域/跟踪参数/公共后缀/平台号识别/反爬策略 │
└────────────────────────────────────────────────────────────────────────┘
```

多需求并行:`NeedProfile` 表已有;`Source.serves_needs` 已支持一源多需求;
所有带 `need_id` 的表已隔离。缺的是**调度/启动/首次流程按"全部激活需求"循环**,
以及**默认需求**从 40 处字面量收敛到 `settings.default_need_id` 一处。
